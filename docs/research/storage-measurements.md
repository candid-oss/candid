# 存储实测：空间花在哪里与验证结果

**状态**：已完成（2026-11-18 至 2026-11-19）。结论被 [data-model](../specs/data-model.md) 采用（截图 WebP、录音 AAC、数据库瘦身、按年龄降级）。

**问题**：迁移后的资料库为什么大？换成什么存储方案能省空间，又不损失可追溯性和检索质量？

**方法**：在真实资料库的副本上测量（2026-11-18），再按新结构转换副本，实测或按实测比例估算（2026-11-19）。截图和录音的编码对比各用少量真实样本。只报计数和大小，不含内容。

## 观察与数据

### 现状：空间花在哪里（2026-11-18）

对迁移后资料库的测量，覆盖 2026-08-17 至 11-18 共 94 天，总计 6.8 GB：

| 项目 | 规模 | 问题 |
|---|---|---|
| 截图原件（JPEG） | 14,610 张，4.6 GB，平均 328 KB，约 1900×1230 | 占全部空间约七成；有采集的日子平均每天约 1,240 张 |
| 旧桌面台账的截图 | 481 MB | 切换到直写后仍保留的重复副本 |
| `store_meta` | 256 MB | 截屏片段的输入（`screen.input`）和修订（`screen.revision`）各 1,015 条，两份等大；键值配置表被当成文档仓库 |
| `episode_evidence` | 114 MB | 证据定位（`selector_json`）平均 12.6 KB，最长 113 KB，存了正文副本 |
| `source_cursors` | 112 MB | 单个 AI 会话的同步进度最长 6.5 MB |
| 派生 JSON 原件 | 19,739 个，435 MB | 识别结果整份存成文件 |
| 日志类表 | 访问日志 15.7 万行，变更 15.2 万行，AI 会话条目 14.3 万行 | 只增不减，没有保留期 |
| 录音（WAV） | 54 段，140 MB | 平均每段 2.6 MB，未压缩 |

已经起作用的：段落去重。96,852 次文字引用只存了 39,606 段正文，压缩约 2.4 倍。

另外有十张表是空的或几乎是空的：`memories`、`memory_sources`、`entity_mentions`、`digests`、`proposals`、`record_audit`、`record_revisions`、`record_selected`、`ingest_conflicts`、`entities`（2 行）。

> 结论：空间问题集中在截图编码和重复保存，数据库问题集中在「把大段内容塞进不该放的地方」。两者都靠结构和策略解决，不需要牺牲可追溯性。

### 截图编码对比（2026-11-18）

用 12 张真实截图（约 1920×1130）实测：

| 格式 | 平均大小 | OCR 字符召回（平均 / 最低） |
|---|---|---|
| 现在的 JPEG | 364 KB | 基准 |
| JPEG 质量 40 | 185 KB | 94.5% / 77.0% |
| **WebP 质量 60** | **122 KB** | 92.0% / 82.4% |
| HEIC 质量 50 | 153 KB | 94.0% / 90.0% |
| AVIF 质量 50 | 124 KB | 92.0% / 85.1% |

- 各格式的识别率差距在 OCR 本身的波动范围内，裁出同一块文字区域肉眼看不出差别。实测是在已有 JPEG 上二次压缩，从采集的原始画面直接编码只会更好。
- 选 WebP：约为现在的三分之一，编码快；Windows、浏览器都能直接显示，以后的网页界面和 Windows 版不需要转码。HEIC 在 Windows 上要额外装扩展，浏览器基本不支持；AVIF 大小相当但编码慢；JPEG 同样清晰度下约大一半。

### 录音编码对比（2026-11-18）

一段 30 秒、48 kHz 单声道录音：WAV 2.9 MB，Opus 24 kbps 89 KB，AAC 32 kbps 128 KB，MP3 32 kbps 120 KB，都缩小二十倍以上。

- 选 AAC（`.m4a`），单声道，48 kbps，采样率不低于 16 kHz：Mac 和 Windows 都能用系统自带的编码器，到处都能播放。转写模型识别前都重采样到 16 kHz 单声道，更高的采样率用不上；48 kbps 比测试的 32 kbps 多留余量，体积约为 WAV 的十五分之一。
- 不选 MP3：低码率下最差，32 kbps 会把频段砍到 8 kHz 左右。Opus 同样清晰度下更小，但 Mac 上要额外带编码库。
- 放行条件：同一段录音压缩前后，转写结果基本一致，且声纹匹配分数下降不超过阈值。声纹模型对压缩失真比转写更敏感；但目前声纹识别本身的信度偏低，要先把它的基线做可靠，这一条才有判别力。

### 验证结果：转换后的空间（2026-11-19，在资料库副本上）

按新结构转换副本后实测或按实测比例估算：

| 部分 | 现在 | 转换后 | 依据 |
|---|---|---|---|
| 数据库 | 1,021 MB | 约 475 MB | 实测 569 MB（片段输入去重并改存引用、证据定位改为编号和区间、同步进度只存位置、删空表）；`screen.text` 里嵌的证据同样处理，实测 103 MB → 8 MB |
| 截图 | 4,685 MB | 约 1,570 MB | WebP 实测比例；采集时去重的收益未计入 |
| 旧台账 | 539 MB | 0 | 退役 |
| 派生 JSON | 435 MB | 约 54 MB | zstd 实测压缩 8 倍；入表后更小 |
| 录音 | 140 MB | 约 10 MB | AAC 48 kbps |
| **合计** | **约 6.8 GB** | **约 2.1 GB** | 减少约七成 |

缩略图（宽 480，WebP）实测平均 11 KB。现有截图都在 30 天内，按年龄降级要到之后才起作用。

### 验证结果：功能查询（2026-11-19）

经核心对外的查询接口：

| 功能 | 结果 |
|---|---|
| 回忆与检索 | 可用，关键词和人名检索都在 1 秒内返回带出处的结果；结果标为扫描受限，长时间范围要靠索引改进 |
| 给 agent 的上下文 | 某一时刻前后的事件和焦点段落可用（0.2 秒）；缺近期的片段摘要 |
| 日回顾 | 时间分布可用；**11 月 13 日之后没有新片段**：片段摘要功能被关闭后，954 个摘要任务以 `feature_disabled` 取消，24 个因模型接口返回 400 失败；已有片段也只有标题、没有摘要 |
| 承诺与待办 | **没有数据**：抽取还没有实现 |
| 人物和项目页 | **几乎没有数据**：实体只有 2 个（来自声纹登记） |

> 结论：存储结构的改动方向成立，空间能减少约七成，查询速度足够。五个功能的主要缺口不在 schema，在派生流程：片段生成停了，抽取和实体层还没做。schema v1 落地后，下一步应是把「片段 → 抽取 → 实体」这条流程做通。

### 升级实施后的实测（真实资料副本与资料库）

| 步骤 | 内容 | 结果 |
|---|---|---|
| v9 | 删除只写不读的截屏片段修订；片段输入不再存原文，用时从段落表重建 | 数据库 1,038 MB → 857 MB；8,525 帧、478,589 行重建结果与原文逐字一致 |
| v10 | 片段输入和证据定位不再逐行重复事件 ID 和段落族哈希；证据定位改为 `screen-selector/2` | v8 → v10 共 1,038 MB → 701 MB，首次打开升级 13 秒；478,589 行证据还原后与原文逐字一致 |
| 一次性转换 | 已有截图转 WebP、派生 JSON 压缩（raw DEFLATE）、旧 WAV 录音转 AAC、WAL 上限 | 截图 4.91 GB → 1.51 GB（14,610 张，约 4 分钟），派生 JSON 456 MB → 61 MB，WAL 805 MB → 15 MB |
| 旧桌面台账 | 逐字节核对无差异后移出资料库 | 在作者本机执行，约 540 MB |
| 待测 | AI 会话条目文件路径和哈希只存一次、条目引用编号 | 实测直接逐行转出会让表从 82 MB 涨到 221 MB，必须先去掉重复；`screen.text` 内嵌证据（约 100 MB）改引用尚未做 |

## 结论

- 存储结构的改动方向成立，空间可减少约七成（6.8 GB → 约 2.1 GB），检索速度足够。
- 截图改 WebP（质量约 60）、录音改 AAC（48 kbps）、数据库瘦身、日志设保留期，由 [data-model](../specs/data-model.md) 采用；对应决定见[决定流水](../decisions/log.md)。
- 五个初期功能的主要缺口不在 schema，在派生流程（片段生成停了，抽取和实体层未做）；该缺口由 [curation](../specs/curation.md) 与 [people-items](../specs/people-items.md) 采用。
- 样本小（12 张截图、一段录音），数值都要在你的数据上再实测后定，未验证的部分见 [roadmap](../roadmap.md)。
