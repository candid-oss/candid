# AI v1 调研结论与实测记录

**状态**：已完成（2026-11-20 至 2026-11-21）。结论被 [curation](../specs/curation.md)、[models](../specs/models.md) 和 [people-items](../specs/people-items.md) 采用；2026-11-25 的真实数据对照实验另见 [data-layer-lab](../plans/data-layer-lab.md)（仍在进行）。

**问题**：回消息和抽日程的数据到底在哪里、质量怎么样？截图读取应该怎么分工（OCR 与视觉模型）？各环节哪些必须调模型，调多少次？

**方法**：在本机真实数据的副本上做调研和样例回放（`excerpt_replay`），只报计数和现象，不贴内容。模型为 LM Studio 上的本地小模型（gemma-4 系列等）。原文来自旧计划 `ai-v1-plan` 的「调研结论」与「进度」中的实测部分，以及 `data-layer-v1` 的调用量估算。

## 观察与数据

### 调研结论（2026-11-20，本机最近 7 天数据）

| 观察 | 含义 |
|---|---|
| 消息主要在**微信、QQ**（微信约 9.5k 条屏幕事件/周）；邮件很少（收约 185、发 12） | 回消息和抽日程的主战场是**聊天应用的屏幕内容**，邮件是次要来源 |
| 微信的 AX 几乎拿不到正文（只有窗口标题，`text_status: partial`、`nodes: 0`），正文全靠截图 OCR | 聊天结构必须从图像里恢复 |
| OCR 的**行坐标在入库时被丢掉**（`core/crates/candid-store/src/desktop.rs` 里 `ocr_lines` 标为 dead_code），侧栏会话列表和正文混成一整块文字 | 第一件事：把坐标留下来 |
| 屏幕片段在生成，但都是 `superseded`、没有摘要；`memories` 为空；实体只有 2 个声纹确认的人 | 抽取链路实际没在运行，不必顾虑兼容旧产出 |
| 核心已经能调 HTTP 模型（`candid-service/src/workflows.rs`，密钥由 App 下发），但**只有一个执行槽**、**不支持流式** | 交互调用会被后台任务挡住，需要优先通道和流式输出 |
| 模型角色全是 LM Studio 上的本地小模型（gemma-4-e4b、nex-n2-mini） | 复用现有角色，不加新的；质量不够就换更强的模型 |
| 写入日历和提醒：提案流程加 EventKit 已经打通（`/local/agenda`、`AIPageModel.swift`） | 后台功能的最后一环已有 |
| 聊天应用的输入框采集目前是 `input_status: disabled` | 想抓到「我发出的」内容，需要对聊天应用开启输入采集 |

### 实测结论：截图摘录（2026-11-20）

本机真实截图副本，gemma-4 本地模型：

- 不给 OCR 时 4B 模型大量认错字（同一个群三帧三个名字）；给 OCR 后名字稳定。
- **模型普遍分不清左右**（26B 也一样），左右改由 OCR 坐标判断后私聊 10/10 正确。
- 26B-A4B 每帧约 2.4 秒，抄写明显好于 E4B。
- 结论：OCR 负责认字和位置，VLM 负责结构。

### 验证数据：AI 可读层骨架（2026-11-20，本机真实数据副本）

升级 59 ms，首次投影 193 条消息 72 ms，查询小于 25 ms。当时的已知缺口：录音消息的说话人还是空的；`ClientScope` 的原始层开关还没加；`excerpts` 还没有写入方。

### 验证数据：整理层来源与时间线库 v12（2026-11-21，本机真实库副本 v10）

升级 1.7 秒，首次同步约 2.6 秒。

### 已知缺口（实测时记录）

- App 的截图 OCR 默认是手动，需要设为自动才有坐标；
- 关键帧偏多（无 OCR 时约 72%）；
- VLM 偶尔漏掉一条；
- 经 LM Studio HTTP 发送 WebP 图片尚未实测（2026-11-25 的对照实验发现 WebP 被 LM Studio 拒收，已修复，见 [data-layer-lab](../plans/data-layer-lab.md)）；
- 录音说话人仍为空（2026-11-21 已接入）；
- 模型调用还没有流式输出。

### 模型调用量估算（2026-11-20 调研，微信约 9.5k 屏幕事件/周）

| # | 调用 | 估算/天 |
|---|---|---|
| 4 | 截图摘录（`vision`） | 150–300 |
| 5 | 条目抽取（`summary`） | 30–80 |
| 6 | 录音标题、摘要 | 0–5 |
| 7 | 人物判断（`summary`） | 0–10（首次回填约 20 批） |
| 8 | 活动块概括 | 20–40 |
| 9 | 日回顾 | 0–1 |

编号对应旧计划的调用清单；估算要跑一周后按 `ai_calls` 的实际数修正上限。

## 结论

- 回消息和抽日程的数据必须从微信、QQ 的截图里恢复；这决定了「OCR 坐标入库、OCR 定位加 VLM 读结构」的方案，被 [curation](../specs/curation.md) 采用。
- 模型分不清左右，名字要靠 OCR 稳定；这两条已写进截图摘录的流程规则。
- 复用现有的 `vision`、`summary`、`agent_chat` 三个角色，质量不够就换模型，不加角色；被 [models](../specs/models.md) 采用。
- 调用量估算被每功能每日调用上限采用；实际数据以 `ai_calls` 为准。
- 2026-11-25 的对照实验修正了其中一些判断（任务形态和确定性校验比模型大小更重要；OCR 负责定位与校验而不是认字），见 [data-layer-lab](../plans/data-layer-lab.md)，本文不改写。
