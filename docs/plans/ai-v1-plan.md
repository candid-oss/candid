# AI 功能 v1 实施计划：内容抽取 → 自动日程/备忘/提醒 → 基于历史回消息

> 工作计划，不是规格。原则：**先打通，再打磨**。每个里程碑结束都有一个能用的功能；质量靠「样例回放 + 人看」和调提示词，不建严格评估集。跨平台：除标明「平台层」的部分，全部在 Rust 核心里做。

## 进度

- **2026-11-20 · AI 可读层骨架（M1 的一部分）**：`conversations` / `messages` / `message_sources` / `excerpts` / `excerpt_sources` 派生表和整理层全文索引（时间线库 v11，`core/crates/candid-store/src/curated.rs`）；邮件和录音转写投影成消息（后台 tick 增量同步）；新工具 `find`、`conversations`、`conversation`、`evidence`，已进 MCP 目录和 Pi，系统提示改为优先读整理层；OCR 行坐标随 `image.text` 入库（payload `boxes`）。在本机真实数据副本上验证：升级 59ms，首次投影 193 条消息 72ms，查询 < 25ms。
  - 已知缺口：录音消息的说话人还是空的（标签存在 `media_recognitions` 的 conversation 结果里，下一步接上）；`ClientScope` 的原始层开关还没加，旧工具暂时照常可用；`excerpts` 还没有写入方（M2）。
- **2026-11-20 · 截图摘录与「帮我写」打通（M2、M3 v1）**
  - 截图 → 关键帧（有 OCR 比行，没有 OCR 比 96×60 灰度缩略图）→ `vision` 摘录（提示词 `core/prompts/screen-excerpt.md`，数据目录 `prompts/` 下同名文件可覆盖）→ **OCR 坐标定左右和顺序** → 与对话末尾对齐、和最近 60 条去重后追加。新功能开关「屏幕对话与摘录」（默认关、每日上限 300），不加模型角色。
  - 实测结论（本机真实截图副本，gemma-4 本地模型）：不给 OCR 时 4B 模型大量认错字（同一个群三帧三个名字）；给 OCR 后名字稳定。**模型普遍分不清左右**（26B 也一样），左右改由 OCR 坐标判断后私聊 10/10 正确。26B-A4B 每帧约 2.4 秒，抄写明显好于 E4B。结论：OCR 负责认字和位置，VLM 负责结构。
  - `/local/compose` + 「帮我写」面板（默认 ⇧⌘J）：当前对话最近 30 条 + 你的 8 条历史发言 + 选中文字/输入框草稿 → `agent_chat` 一次调用 → 插入到原输入框，不代发。
  - 样例回放：`cargo run -p candid-store --example excerpt_replay -- select|ocr|apply|compose …`，只用于真实库的**副本**。
  - 已知缺口：App 的截图 OCR 默认是手动，需要设为自动才有坐标；关键帧偏多（无 OCR 时约 72%）；VLM 偶尔漏掉一条；经 LM Studio HTTP 发送 WebP 图片尚未实测；录音说话人仍为空；模型调用还没有流式输出。
- **2026-11-21 · 数据层规划定稿**：人物归一、条目层（新建 `items`）、整理层补齐的来源、模型调用清单与预算、实施顺序见 [数据层与 AI 处理规划 v1](data-layer-v1.md)，其中的决定替代本文 M4 第 2、4 条和 M1 第 1 条的粗略写法。
- **2026-11-21 · 整理层来源与时间线库 v12**：`conversations.kind` 加 `agent`；新建 `items`、`item_changes`、`item_sources`（字段与触发器见 [数据层规划](data-layer-v1.md#21-存储时间线库-v12)）；录音说话人、AI 提示词会话、浏览器和文档类应用的 AX 正文摘录接入 `curated_sync`；`find` 加 `conversation_kind`，`conversations` 可按 `agent` 过滤。在本机真实库副本（v10）上验证：升级 1.7s，首次同步约 2.6s。
- **2026-11-25 · 真实数据对照实验**：新增 `candid-lab`（样本包克隆、驱动生产后台 worker、模型回复缓存、dump/diff、OCR 落地率），在本机与硅基流动上对比了截图读取的读法与模型、整条数据层联跑；修复 WebP 被 LM Studio 拒收、输出上限 1024、积压乱序、会话拆碎、幻觉消息、AX 噪声、人物误合并等问题。结论、目标形态与路线见 [数据层对照实验 v1](data-layer-lab.md)。
- 下一步：按数据层规划的顺序——调度地基（两条通道、每功能预算）→ 不调模型的来源 → 人物规则层 → 条目抽取。

## 0. 调研结论（2026-11-20，本机最近 7 天数据）

| 观察 | 含义 |
|---|---|
| 消息主要在**微信、QQ**（微信约 9.5k 条屏幕事件/周）；邮件很少（收约 185、发 12） | 回消息和抽日程的主战场是**聊天应用的屏幕内容**，邮件是次要来源 |
| 微信的 AX 几乎拿不到正文（只有窗口标题，`text_status: partial`、`nodes: 0`），正文全靠截图 OCR | 聊天结构必须从图像里恢复 |
| OCR 的**行坐标在入库时被丢掉**（`core/crates/candid-store/src/desktop.rs` 里 `ocr_lines` 标为 dead_code），侧栏会话列表和正文混成一整块文字 | 第一件事：把坐标留下来 |
| 屏幕片段在生成，但都是 `superseded`、没有摘要；`memories` 为空；实体只有 2 个声纹确认的人 | 抽取链路实际没在运行，不必顾虑兼容旧产出 |
| 核心已经能调 HTTP 模型（`candid-service/src/workflows.rs`，密钥由 App 下发），但**只有一个执行槽**、**不支持流式** | 交互调用会被后台任务挡住，需要优先通道和流式输出 |
| 模型角色全是 LM Studio 上的本地小模型（gemma-4-e4b、nex-n2-mini） | 复用现有角色，不加新的；质量不够就换更强的模型 |
| 写入日历和提醒：提案流程加 EventKit 已经打通（`/local/agenda`、`AIPageModel.swift`） | 后台功能的最后一环已有 |
| 聊天应用的输入框采集目前是 `input_status: disabled` | 想抓到「我发出的」内容，需要对聊天应用开启输入采集 |

## AI 可读层：AI 读什么（贯穿所有里程碑）

**问题**：现在给 agent 的工具（`pv_timeline`、`pv_search`、`pv_get_event`，见 `core/crates/candid-store/src/query/dispatch.rs`）直接面对原始事件。`timeline` 默认的 `level=event` 会把窗口切换、截图、OCR 块一条条返回，`search` 搜的也是原始屏幕文字。AI 读到的大多是噪声，而且很费 token。

**原则**：AI 默认只读**整理好的对象**；原始记录只作为证据，按需下钻，并且单独授权。

### 分三层

| 层 | 内容 | 谁读 |
|---|---|---|
| **原始层** | 截图、OCR 块、窗口和应用切换、屏幕文字帧、音频分段 | 只给整理流程用；AI 通过 `evidence` 下钻，需要单独授权 |
| **整理层**（AI 默认读这一层） | 对话（消息）、摘录、活动块（见下表） | 内置 AI 和外部 agent 默认可读 |
| **理解层** | 人、条目（日程/提醒/备忘/承诺）、汇总 | 同上 |

整理层的对象：

| 对象 | 内容 | 来源 |
|---|---|---|
| **对话** `thread` + `message` | 「什么时候，我和谁，在哪个应用，说了什么」：`{应用, 会话, 发送人(人物实体或名字), self/other, 时间, 正文}` | 微信、QQ 截图摘录（M2）；邮件；会议和录音转写（说话人当发送人）；AI 会话 |
| **摘录** `excerpt` | 读过或写过的文档、网页正文：`{应用, 标题, URL, 时间段, 正文摘录}` | 浏览器、文档类应用的 AX 主内容区或截图摘录 |
| **活动块** `episode` | 「14:00–15:30 在 Chrome 查 X、写 Y」这一级的时间块和一句话概括 | 窗口和应用切换只用来生成它，本身不对 AI 暴露 |

所有来源都投影成同一种形状：邮件、转写、截图里的聊天，在 AI 看来都是 `message`，不用关心它原来是哪种事件。

### 存储

- `threads` 已经有 `chat`、`mail_thread`、`meeting`、`recording` 这几种，直接当对话的容器。
- 新增派生表 `messages`：`thread_id, seq, sent_ms, actor(self/other), sender_label, sender_entity_id, text, producer, status, evidence_json`。邮件和转写从已有事件投影进来，截图聊天由 M2 写入。和其他派生表一样：可以整体重算，你的纠正单独保存。
- 新增派生表 `excerpts`：`excerpt_id, key(URL 或 应用+标题), start_ms, end_ms, text, producer, evidence_json`。
- **整理层单独建全文索引**，和原始文字的 `text_fts` 分开，搜索默认只搜整理层，排序也就不会被界面文字干扰。

### 接口（MCP 和 Pi 用同一套，替换现在默认暴露的工具）

| 工具 | 返回 |
|---|---|
| `find` | 在整理层和理解层里搜索，可按类型、人、应用、时间过滤 |
| `conversations` / `conversation` | 按人、应用、时间列出对话；取一段对话的消息（分页） |
| `day` | 某天或某个时段的活动块和汇总，替代按事件列出的 `timeline` |
| `person` | 人物卡：别名、最近往来、未结条目、备忘 |
| `items` | 日程、提醒、备忘、承诺 |
| `evidence` | 给一个对象，下钻到它依据的原始记录（OCR 文字、转写原文）。需要单独的 `raw` 授权；图片还需要 `media` 授权 |

- 授权：`ClientScope` 加一个层级开关，默认只开整理层和理解层；内置 Pi 和新注册的外部 agent 默认都不开 `raw`。现有的 `pv_timeline`、`pv_get_event` 降级成 `evidence` 下面的能力，过渡期保留，不再默认暴露。
- 每个返回对象都带 `id` 和简短的出处说明（应用、时间），可以引用；原始事件 ID 不直接暴露给 AI。
- M3 的 compose 预取、M4 的抽取，都只读这一层，不再直接扫原始事件。

## 1. 里程碑

| 里程碑 | 交付 | 依赖 |
|---|---|---|
| **M1 地基** | 模型优先通道和流式输出、提示词文件化、样例回放工具；OCR 坐标入库 | — |
| **M2 截图摘录** | 大量截图 → 去重选关键帧 → VLM 出干净摘录（聊天带发送人）→ 按会话/页面合并，可在时间线查看 | M1 |
| **M3 回消息（打字版）** | 快捷键 → 输入指令 → 结合当前会话和历史生成草稿 → 写回输入框。**也就是 demo 那种体验** | M1、M2 |
| **M4 日程/提醒/备忘** | 从消息、邮件、录音里自动抽取，出现在「待你处理」，一键加到日历或提醒 | M2 |
| **M5 闭环与语音** | 按住说话；发出的内容回流抽取；人物卡；到期推送 | M3、M4 |

M3 排在 M4 前面，是为了尽早做出能直接感受到的体验；两者共用 M2 的结构化消息。

## 2. M1 地基

1. **模型调用**（`candid-service/src/workflows.rs`）
   - 把单一执行槽拆成两条通道：`interactive`（compose、问答）和 `background`（抽取、摘要），交互调用不再等后台。
   - 流式输出：支持 openai-chat 和 anthropic-messages 两种 SSE，本地通道按块推送给 App。
2. **不加新角色**，复用现有的：截图摘录用 `vision`；抽取用 `summary`；回消息和问答用 `agent_chat`。用户要管的模型设置不增加。
3. **提示词文件化**：把 `core/workflows/prompts.json` 拆成 `core/prompts/<name>.md`，加上版本号；开发时支持从数据目录里的覆盖文件热加载，改提示词不用重新编译。
4. **样例回放**：`candid dev replay <prompt> <case-dir>` 用某个提示词跑一组保存好的输入，把输出和上一次的结果并排显示。这就是「轻量测试集」，从真实数据里挑样例存到本机，不进仓库。
5. **AI 可读层的骨架**：`messages`、`excerpts` 两张表和整理层索引；先把邮件和录音转写投影进 `messages`，新工具 `find`、`conversations`、`conversation`、`evidence` 先上线，其余工具随后续里程碑补齐。
6. **OCR 坐标入库**：`RecognitionResult.ocr_lines` 存进 `image.text` 的 payload（或作为 blob 引用），格式统一成 `{text, x, y, w, h}`，坐标按 0–1000 归一化。不回填历史数据。

## 3. M2 内容抽取：从大量截图里取出有效信息

目标：每个窗口在一段时间内的**干净摘录**。聊天类是 `{会话, 发送人(self/other/名字), 时间, 正文}`，文档、网页类是正文摘录，界面外框不要。v1 用 VLM 跑通，再逐步用便宜的办法替掉 VLM 调用。

### 3.1 v1：去重 → 关键帧 → VLM → 合并

1. **帧去重，选关键帧**（规则，不花 token）
   - 同一窗口的连续截图：沿用桌面采集已有的「画面相同」判定，再加一层 OCR 文字比较（复用 `screen_cleanup.rs` 的 SimHash）。和上一张已处理的关键帧相比没有新文字的，跳过。
   - 去抖：画面滚动或连续变化时，只取停稳后的那一帧（例如 2 秒内没有新变化）。
   - 每天的 VLM 调用设上限，超出的帧留到空闲时处理或直接放弃。
2. **VLM 摘录**（`vision` 角色）
   - 输入：关键帧截图 + 这张图的 OCR 文字（作为参考，帮助小模型认准字）+ 这个窗口上一次的摘录尾部（帮它对齐，只输出新内容）。
   - 输出固定 JSON：`{kind: chat|doc|web|other, title, messages: [{sender, time, text}] | excerpt, ignored_ui: bool}`。提示词规定：只要主内容区；聊天气泡靠右是我；不要侧栏、按钮、会话列表。
3. **合并**：同一会话或页面的前后摘录按 `(会话, 发送人, 规范化正文)` 去重后追加，写入 AI 可读层的 `messages`（`threads(kind='chat')` 下）或 `excerpts`，记下来源截图作为证据，可以重算。
4. **我发出的**：微信输入框是 `AXTextArea`，可以读到值。输入框从有字变空、同时摘录里出现一条一样的 self 消息，就判为「已发送」。需要用户对聊天应用开启输入采集。
5. **验证**：挑约 15 个真实画面（微信私聊、群聊，QQ，浏览器文章，腾讯会议聊天）存成样例，用回放工具人工看一遍，重点看发送人归属和有没有混进界面文字。

### 3.2 之后的优化（跑通后按成本和效果挑着做）

- **只看变化区域**：和上一关键帧做像素差，只把变化的区域裁出来给 VLM（聊天里通常只是底部几条新消息），token 大幅下降。
- **OCR 坐标 + 版面规则**：坐标入库后（M1），按 x 聚类分栏、跨帧位置稳定判外框、按气泡左右判发送人，规则拿得准的就不调 VLM。
- **AX 优先**：浏览器、Slack、邮件这类 AX 能读到结构的，直接用 AX 主内容区，完全不用图。
- **按窗口缓存版面**：同一应用的分栏位置很稳定，学一次就能直接裁主区。

## 4. M3 主动功能：基于历史回消息

1. **平台层**（Swift，以后 Windows 另做）
   - 全局快捷键唤起浮动输入条（复用 `GlobalHotkeys.swift`、`FloatingControl.swift`）。
   - **按下快捷键的那一刻**取快照：前台应用、窗口标题、焦点输入框的值、选中文字、一张当前窗口截图（用于微信这类 AX 读不到的应用）。
   - 写回：剪贴板暂存 → 模拟 Cmd+V → 恢复原剪贴板。**不自动发送。**
2. **核心接口** `POST /local/compose {instruction, snapshot}`，流式返回
   1. 认出会话：当前截图实时做一次摘录（M2 的同一套流程），并合并库里这个会话最近的消息；
   2. 认出人：会话名 → 人物实体（精确别名）；
   3. 预取：这个会话最近 30 条消息，和这个人之间的未结条目与备忘（M4 之后才有），我以前回给他的 3 条消息（当风格示例），用指令关键词搜到的前 5 条结果；
   4. 用 `agent_chat` 角色**一次调用**，流式生成；
   5. 返回「上下文标签」，在浮层上显示这次用了哪些内容，每个标签可以删掉后重新生成。
3. **当前屏幕问答**：同一个接口。指令是问题时（模型判断，或者设两个快捷键），输出答案而不是草稿。
4. 对外也提供 MCP 工具 `compose_context`（只返回上下文包，不生成），外部 agent 可以复用。

## 5. M4 自动功能：日程、提醒、备忘

1. **抽取任务**（`summary` 角色，后台通道）
   - 输入：一个会话 10 分钟内没有新消息时，取这段新消息；另外还有邮件串、录音转写、AI 页的笔记。
   - 同时给模型看「这个人已有的未结条目」，让它可以输出 `update` 或 `done` 来指向已有条目。去重和变更检测就靠这一步，主要通过调提示词解决。
   - 输出：`{type: event|reminder|memo|update|done, owner: self|other, counterpart, when_text, when_iso, text, evidence}`。时间以**消息发出的时间**为基准来解析。
   - 只抽明确的约定和事实。
2. **存储**：`memories` 作为候选写入（日程和提醒用 `commitment`，备忘用 `fact` 或 `reference`）。`memories` 现在只有 `text` 一个内容字段，需要加一个结构化字段（时间、对方、类型），这是一次小的 schema 升级。
3. **呈现**：扩展 AI 页「待你处理」，分成日程、提醒、备忘三栏。要素齐全的条目可以一键加到日历或提醒（走现有的提案流程和 EventKit）。被忽略的条目回传给下一次抽取。
4. **人物**：微信会话名、邮箱 → 人物实体（`entity_aliases` 加一种会话名别名），消息和条目都挂到人身上。

## 6. M5 闭环与语音

- **语音**：按住快捷键说话，用系统本地听写（SpeechAnalyzer / SFSpeechRecognizer）转成指令，复用 M3 的整条链路。
- **闭环**：M2 捕获到「我发出的」消息后，优先进入抽取；插入草稿时如果里面有时间约定，浮层顺带问一句「加到日历？」。
- **人物卡**：实体 + 最近往来 + 未结条目 + 备忘，同时作为 compose 预取的来源。
- **推送**：提醒到期发本地通知（`AutomationNotifier.swift`）；会前简报放在最后。

1. 现有的 `vision`、`summary`、`agent_chat` 是否换成更强的模型（本地 4B 级别做截图摘录和写作，质量可能不够）。不加新角色，只是换模型。
2. 是否对聊天应用开启输入框采集（「我发出的」内容要靠它）。
3. `memories` 加结构化字段的这次 schema 升级。
