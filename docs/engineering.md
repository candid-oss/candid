# 工程规范

**状态**：已生效（2026-11-26 起）。标「靠自觉」的规则没有自动检查。

本文规定所有改动都要遵守的东西：设计原则、代码规范、测试秩序、各类改动的做法、完成的定义、多个会话并行时的规则、发布。
它不规定某个模块的具体行为（见[规格](specs/README.md)），不规定文档怎么写（见[文档规范](standard.md)）。
给 coding agent 的执行摘要在 [AGENTS.md](../AGENTS.md)；两处冲突时以本文为准，并修正 AGENTS.md。

<a id="why"></a>

## 1. 这份规范的前提

仓库的主人只做上层设计，不读代码。代码几乎全部由 coding agent 写，常常是几个会话同时写。所以：

- **判断有没有改坏，只能靠测试。** 主人看不出一段代码对不对，他只能看到检查过没过、文档和实际一不一致。
- **规则必须少，且尽量能自动检查。** 写了没人查的规则等于没写。本文每条规则都标了检查方式；没有检查的标「靠自觉」，这类规则越少越好。
- **规范不能拖慢开发。** 不收风格偏好。一条规则进来的标准是：违反它会让数据出错、让契约破裂、让主人失去对系统的判断，或者让下一个平台多写一遍。

<a id="principles"></a>

## 2. 设计原则

八条。做设计取舍时按这个顺序想；两条冲突时，编号小的优先。

### 2.1 数据是用户的

数据只在本机，没有账号、没有遥测、没有用户没配置的网络请求。数据能整体带走，格式公开。

- 怎么用：新增任何网络请求之前，确认它是用户配置出来的（模型来源、IMAP、语音服务）。新增任何存储位置都要进[数据位置清单](data-migration.md)，并说明备份带不带走。
- 反例：为了排查问题加一个上报；把状态存进一个清单之外的缓存文件。
- 检查：备份往返测试（`core/crates/candid-cli/tests/migrate.rs`）；其余靠自觉。

### 2.2 采集到的内容是证据，不是指令

屏幕、网页、消息、邮件里的文字随时可能包含想操纵 AI 的内容。

- 怎么用：这类文字只放在提示词的数据区。执行者不带终端和文件写入工具。写操作只走提案，用户批准前不执行。
- 反例：把一封邮件的正文拼进系统提示；让技能直接改日历。
- 检查：Agent 端到端测试里有「数据中的指令不被执行」和「越权被拒绝」两项。

### 2.3 一份数据，多个出口

App、挂接的 Pi、外部 agent 读同一份整理好的数据，经同一套范围过滤与审计。

- 怎么用：界面要展示新东西时，先让查询工具能给出它，再让界面去调。不为某一个出口单独存一份或单独算一遍。
- 反例：界面自己从原始事件里拼一个「今天」视图，而 MCP 的 `day` 工具给出的是另一个结果。
- 检查：全流程测试经 MCP 查询验证结果。

### 2.4 逻辑在核心，平台层薄

整理、去重、抽取、调度、模型调用、计费都在 Rust 核心。平台层只做界面、系统采集、系统权限和平台能力。

- 怎么用：判断标准是「这段代码换到 Windows 要不要重写一遍？」要，就不该在平台层。
- 反例和现存欠账：见[架构总图](architecture.md#debts)。
- 检查：靠自觉。

### 2.5 扩展只走三个接缝

新数据来源走入库协议，新的消费方走 MCP 或命令行，新的 AI 行为走技能。不做通用插件系统。

- 怎么用：见[架构总图](architecture.md#seams)。三者都不够时才在核心加固定流程。
- 检查：契约快照。

### 2.6 契约靠测试，不靠文字

对外承诺（工具、字段、协议、表结构）都绑定一个快照或测试。文档写了但没有测试的，按「未验证」对待。

- 怎么用：新增一项对外承诺时，同一个改动里加上守护它的测试，并在[契约清单](contracts/README.md)加一行。
- 检查：契约测试、升级测试。

### 2.7 花电有规则

用户没在等的计算都是后台工作。后台工作要有触发事件，有允许运行的条件，同一份输入不过两遍重模型，没有事件不醒。

- 怎么用：新增后台作业时回答三问：谁触发（哪个事件，不能是定时器）、何时允许跑、花多少。
- 反例：每三十秒扫一遍有没有新东西；一张截图先后被两个流程各送一次视觉模型。
- 检查：靠自觉；功耗规则的自动检查正在另行制定（见[待办](roadmap.md)）。

### 2.8 简单优先

三个模型角色，不自造 agent loop，不重复实现核心已有的能力。先打通再打磨。

- 怎么用：加东西之前先问能不能删东西；质量不够先换模型或改提示词，不加角色、不加层。新功能先让完整链路跑通，再抽样检查和优化。
- 反例：为一个新功能加第四个模型角色；在核心里写一个让模型自己选工具的循环。
- 检查：靠自觉。

**功能准入**是产品层面的规则，见[产品定位](product.md#admission)。

<a id="code"></a>

## 3. 代码规范

### 3.1 通用

| 规则 | 检查 |
|---|---|
| 一个改动只做一件事。顺路发现的问题记下来报告，不顺手改 | 靠自觉 |
| 先搜再写：新能力先在 `core/crates/candid-store/src/` 找现成模块扩展 | 靠自觉 |
| 被取代的路径在同一个改动里删掉。不留死代码，不留「以后可能用」的开关 | 靠自觉 |
| 代码注释和提交说明用英文，写「为什么」而不是「做了什么」 | 靠自觉 |
| 界面文字、提示词和面向主人的文档用中文 | 本地化检查 |
| 注释引用文档时写路径加锚点（`docs/specs/storage.md#events`），不写章节号 | 靠自觉 |
| 不提交真实个人数据、录音、截图、数据库、模型、密钥 | `.gitignore`、CI 的密钥扫描 |
| 不在功能改动里顺手格式化整个文件 | 靠自觉。全仓库还没有统一跑过 `cargo fmt`；统一格式化留给一次单独的、没有其他会话在跑时的改动 |

<a id="rust"></a>

### 3.2 Rust 核心

**代码放哪：**

| 要写的东西 | 放哪 |
|---|---|
| 存储、入库、整理、人物、条目、查询、流程状态 | `candid-store` 的现有模块 |
| 需要网络、进程、定时或对外服务的 | `candid-service` |
| 读外部文件或走网络取数据的来源 | `candid-connectors` |
| 命令行入口和整库操作 | `candid-cli` |
| 提示词正文 | `core/prompts/*.md`，不在代码里拼 |
| 固定流程的定义 | `core/workflows/` |

**规则：**

| 规则 | 检查 |
|---|---|
| 依赖方向只有一个：`cli` → `service` → `store`，`connectors` → `store`。`store` 不依赖其他 crate | 编译 |
| 新建 crate 需要先有一条决定。单个文件接近一千行时按职责拆成子模块（目录加 `mod.rs`） | 靠自觉 |
| 表结构只在 `schema.rs` 和 `schema_upgrade.rs` 里改；改了就升 `SCHEMA_VERSION`，带升级测试和失败回滚测试 | 升级测试 |
| 所有写入经入库接口。连接器不直接碰数据库 | crate 依赖 |
| 不新增模型角色。只有 `vision`、`summary`、`agent_chat` | 靠自觉 |
| 模型调用都经核心的模型通道并记账 | 全流程测试的调用快照 |
| 需要「现在几点」的逻辑用注入的时钟（`Clock`），不直接读系统时间，这样测试才能固定时间 | 靠自觉 |
| 新增第三方依赖的许可证要在允许范围内 | CI 的 `cargo deny` |

### 3.3 Swift（Mac App）

| 规则 | 检查 |
|---|---|
| 不写业务逻辑，不直接读写 SQLite，只经 `CandidClient` 的本地通道调用核心 | 靠自觉 |
| 不直接调用模型服务商；要用模型时请核心代为调用 | 靠自觉 |
| 页面只组合 `DesignSystem` 里的组件和样式常量，见[界面规范](specs/design-system.md) | `apps/macos/script/check_style.sh` |
| 界面文字写 `L("中文")`，在 `apps/macos/Resources/Localizable.en.json` 补英文 | `python3 apps/macos/script/localize_sources.py --check` |
| 不再往[架构总图第 9 节](architecture.md#debts)列出的位置加逻辑 | 靠自觉 |

### 3.4 技能与扩展（`agents/`）

| 规则 | 检查 |
|---|---|
| 扩展只把工具调用转发给核心，不在扩展里加逻辑 | 端到端测试 |
| 技能正文是 Pi 与外部 agent 共用的，不写只在某一个执行者上成立的假设 | 靠自觉 |
| Pi 的版本由 `package-lock.json` 锁定，升级是一次单独的改动 | 靠自觉 |

### 3.5 提交说明

- 第一行用英文祈使句说明结果，例如 `Make chat screenshots produce real messages`。
- 正文说明为什么改、改了哪些对外可见的东西。改了契约快照的必须写明变了什么、谁受影响。
- 外部贡献者用 `git commit -s` 签署 DCO，见 [CONTRIBUTING.md](../CONTRIBUTING.md)。

<a id="tests"></a>

## 4. 测试秩序

### 4.1 一条命令

```bash
scripts/check.sh
```

它按改动涉及的目录选出必须跑的检查并执行。`--list` 只看会跑什么，`--all` 全跑，`--base <分支>` 换比较基准。

| 退出码 | 含义 | 该做什么 |
|---|---|---|
| 0 | 全过 | 可以汇报完成 |
| 1 | 有检查失败 | 读输出，改代码 |
| 2 | 有检查因为缺环境没跑成 | 补环境；补不了就在汇报里写明哪项没跑成。**没跑成不等于通过** |

### 4.2 测试分层

| 层 | 位置 | 回答的问题 | 规模 |
|---|---|---|---|
| 模块测试 | `core/crates/*/tests/` | 一个模块的规则对不对 | 约 430 个 Rust 测试 |
| 全流程测试 | `core/crates/candid-service/tests/lifecycle.rs` | 入库到 MCP 查询整条链路通不通；模型收到的输入有没有变 | 一秒以内，超过 30 秒算失败 |
| 契约测试 | `candid-service/tests/mcp_contract.rs`、`candid-cli/tests/contract.rs` | 对外的工具清单、参数和输出有没有变 | 快照比对 |
| 升级测试 | `candid-store/tests/schema_upgrade.rs`、`migration.rs` | 旧库能不能升上来，失败能不能回滚 | 用 `core/fixtures/schema-v*.sql` |
| App 套件 | `apps/macos/script/test.sh` | 样式、本地化、Swift 测试 | 约 400 个 Swift 测试；只在本机跑，CI 上手动触发 |
| Agent 端到端 | `agents/pi-extension/test/e2e.mjs` | 真实核心加锁定版本的 Pi 加回环模型桩：读写、撤销、提案、越权拒绝、数据中的指令不执行 | |
| 语音服务 | `services/voice/tests` | 语音接口 | |
| 文档 | `scripts/check_docs.py` | 链接、双语成对、索引、长度 | |

### 4.3 改什么跑什么

`scripts/check.sh` 执行的就是这张表。

| 改动 | 必跑 |
|---|---|
| 任何 Rust 代码、提示词、流程目录、测试样例 | `cargo test --workspace`（在 `core/` 下） |
| 入库、整理层、截图摘录、活动块、人物、条目、模型调用、提示词 | 上一条，并单独看全流程测试的结果 |
| MCP 工具、命令行、查询输出字段 | 上一条，并看两个契约测试 |
| 表结构 | 升版本，带升级测试（含失败回滚） |
| `apps/macos/` | `swift build --package-path apps/macos`，再跑 `apps/macos/script/test.sh` |
| `agents/` | `node agents/pi-extension/test/e2e.mjs`（先装依赖、先编出核心） |
| `services/voice/` | 语音服务的 pytest |
| 任何 Markdown | `python3 scripts/check_docs.py` |

CI 上每次推送跑：Rust 核心、语音服务（Linux，不含 MLX）、依赖许可证、密钥扫描、文档检查。App 套件不在其中，改了 `apps/macos/` 必须在本机跑。

### 4.4 规则

1. **快照不一致先判断是不是有意的。** 接口或提示词真的要变，才重新生成，并在提交说明里写清楚变了什么、为什么。无意的变化是 bug，改代码而不是改快照。重新生成后逐个看差异，确认只有预期的变化。
2. **不为了让测试通过而放松断言、加跳过或删测试。** 测试本身错了，先说明理由再改。
3. **测试隔离。** 用自己的临时目录和运行目录（`CANDID_RUN_DIR`），永远不碰用户正在用的资料库和运行目录。
4. **测试里的模型只能是本机回环上的桩。** 没有匹配回复的模型请求让测试失败并列出输入。
5. **只用合成数据**，并明确标记。
6. **时间固定。** 涉及时间的测试用注入的时钟，不依赖运行当天的日期。
7. **保持轻量。** 抽样检查关键结果，不追求覆盖率。一个功能至少有一条从入口到出口的测试，比十条内部细节的测试有用。

### 4.5 真实数据

真实资料库只能在副本上试。先复制到临时目录，用 `candid serve --root <副本>` 起一个独立核心；或者用 `candid-lab` 从样本包克隆。永远不要对用户正在用的资料库或运行目录执行写入、迁移或删除。报告真实数据上的结果时只给计数和差异，不贴内容。操作步骤见技能 `.claude/skills/real-data-trial/`。

## 5. 各类改动的做法

每类改动列出必须做全的几件事。漏掉任何一件都不算完成。

### 5.1 加一张表或一个字段

1. 在 `schema.rs` 写新结构，在 `schema_upgrade.rs` 写从上一版升上来的步骤，`SCHEMA_VERSION` 加一。
2. 加升级测试：旧版样例库升上来数据正确；升级中途失败时回滚到旧版，库仍可用。
3. 更新[存储](specs/storage.md)或对应主题的规格。
4. 在[版本记录](changelog.md)的「内部」里写明表结构版本到了几。
5. 同一时间只能有一个改动在升版本，开始前确认没有别的会话也在升。

### 5.2 加或改一个 MCP 工具、命令行命令、输出字段

1. 先确认必要：外部 agent 不会跟着升级。能加字段就不改字段，能加工具就不改现有工具的含义。
2. 实现后重新生成契约快照，逐项看差异。
3. 更新[查询接口](specs/query.md)和[契约清单](contracts/README.md)。
4. 提交说明写明变了什么、谁受影响。

### 5.3 加一次模型调用或一条固定流程

1. 确认用现有三个角色之一。
2. 提示词放 `core/prompts/`，流程定义放 `core/workflows/`。
3. 往 `core/fixtures/lifecycle/world.json` 加能触发它的数据，往 `replies.json` 加回复，在 `lifecycle.rs` 加断言。
4. 回答功耗三问（第 2.7 节）并写进提交说明。
5. 更新[模型调用](specs/models.md)的调用清单和对应主题的规格。

### 5.4 加一个数据来源

1. 归属：读文件、走网络的放 `candid-connectors`；调系统接口的放平台层。
2. 只通过入库协议写入，用合成样例测正常同步、重复同步、中断重试、格式未知时拒绝、撤销授权。
3. 更新[连接器](specs/connectors.md)的清单。
4. 新的磁盘位置或凭据进[数据位置清单](data-migration.md)。

### 5.5 加一个页面或界面元素

1. 需要的数据先由核心的查询工具或本地通道给出。
2. 只用 `DesignSystem` 的组件；缺组件就先加组件。
3. 文字用 `L("中文")` 并补英文。
4. 跑 `apps/macos/script/test.sh`。

### 5.6 加一个技能

1. 在 `agents/skills/<名字>/SKILL.md` 写正文和前置字段。
2. 只用现有工具；需要新工具按 5.2 做。
3. 跑 Agent 端到端测试。
4. 更新[固定流程与 agent](specs/workflows.md)的技能清单。

<a id="done"></a>

## 6. 完成的定义

一个改动算完成，要同时满足：

- [ ] `scripts/check.sh` 退出码为 0；或者明确说明了哪项没跑成、为什么。
- [ ] 第 5 节里对应类别的每一步都做了。
- [ ] 受影响的规格、契约、地图、模块 README 已同步，双语文档两版都改了。
- [ ] 版本记录的「未发布」加了一条；待办里对应的项删了。
- [ ] 没有顺手改无关的东西；发现的无关问题记进了待办的「已知问题」或写在汇报里。
- [ ] 汇报用主人能判断的话写：用户能看到什么变化、跑了哪些检查和结果、哪项没跑成、有什么需要主人决定。不贴代码。

<a id="sessions"></a>

## 7. 多个会话同时工作

| 规则 | 原因 |
|---|---|
| 每个会话在自己的分支和工作目录里做，不在主目录里留未提交的改动 | 主目录里的未提交改动会挡住别的分支合并 |
| 不改别的会话正在改的文件 | 避免互相覆盖 |
| 要动共享文件（`AGENTS.md`、`README`、表结构、快照、`changelog.md`）时改动尽量小，并在汇报里点名 | 这些文件最容易冲突 |
| 升表结构版本的改动一次只能有一个在进行 | 版本号会撞 |
| 合并进主分支之前，在合并后的结果上重新跑一遍 `scripts/check.sh` | 各自通过不等于合在一起通过 |
| 合并由主人决定，会话不自行合并别的会话的分支 | |

<a id="release"></a>

## 8. 发布

1. 确认主分支上 `scripts/check.sh --all` 通过，App 套件在本机通过。
2. 把[版本记录](changelog.md)的「未发布」改成版本号和日期，上面新开一个空的「未发布」。
3. 把 `core/Cargo.toml` 的 `version` 改成同一个版本号。
4. 推送标签 `vX.Y.Z`。`.github/workflows/release.yml` 会构建一个草稿发布（仅 Apple Silicon，临时签名，未公证）。
5. 把[待办](roadmap.md)里「下一版」的剩余项移到新的下一版或「之后」。

版本号规则见[文档规范](standard.md#versions)。
