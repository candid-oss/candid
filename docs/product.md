# 产品定位

**状态**：第 1 至 6 节是已定的方向；第 7、8 节标「待定」的条目还没有拍板，不要当作既定方向去实现。

本文回答：Candid 是什么、要验证什么、为谁提供什么价值、坚持什么、不做什么、一个功能该不该做、怎么知道做对了。
它不描述系统怎么构成（见[架构总图](architecture.md)），不列具体要做的事（见[待办](roadmap.md)）。

方向只由仓库的主人改。其他文档和功能与本文冲突时，以本文为准。

<a id="what"></a>

## 1. 是什么

Candid 是本地优先、开放、可迁移的个人上下文底座：把你在电脑上的一天整理成干净、有出处、可纠正的数据，交给你自己选择的 AI。

它同时是两样东西，共用同一份数据：

| | 是什么 | 给谁 |
|---|---|---|
| 底座 | 采集、整理、查询、权限与审计。产品的本体 | 任何能接 MCP 或命令行的 agent |
| 自带界面 | 一个薄的 Mac App | 不接任何外部 agent、也想直接得到价值的人 |

**它不是什么：** 不是又一个聊天助手，不是云端的个人 agent 服务，不是录屏回放工具。回放不是目的；让 AI 真的了解你才是。

<a id="question"></a>

## 2. 要验证的问题

**采集到的数据，能不能变成 AI 对一个人的认知？**

这是项目存在的理由。「认知」指的是：AI 不用你重新交代背景，就知道你在做什么、和谁往来、答应过什么、关心什么，并且说得出依据。

这个问题拆成四段，每一段都要成立：

| 段 | 要成立的事 | 失败的样子 | 现状 |
|---|---|---|---|
| 采得到 | 该有的来源都进来了，不费电、不打扰、用户始终知道在不在记录 | 只有截图，漏掉没打开过的邮件和消息；风扇常转；用户不敢开 | 屏幕、截图、录音、邮件、日历、AI 会话已有。见[连接器](specs/connectors.md) |
| 理得清 | 原始记录变成对话、消息、摘录、活动块、人物、条目，每条能回到出处，错了能改 | 一堆重复的截图文字；同一个人三个名字；AI 编出没发生过的事 | 整理层已有主干，质量在用真实数据对照。见[整理层](specs/curation.md)、[人物与条目](specs/people-items.md) |
| 用得上 | AI 拿到这些之后，回答和行动明显更懂你 | 接上了但 AI 的回答和没接一样；要用户自己翻时间线 | MCP 工具、技能、AI 页已有；有没有「明显更懂」还没有衡量办法（第 7 节） |
| 带得走 | 数据是你的，能整体导出给别的工具读 | 换一个工具就要从头开始 | 整库备份已有；开放格式导出未实现 |

四段里「带得走」是和系统厂商自带 AI 的根本区别。厂商的 AI 可以做得很好，但数据导不出来，这符合厂商的利益。Candid 存在的一部分理由就是证明可以不这样。

<a id="users"></a>

## 3. 为谁，提供什么

两类用户不是两套功能，而是同一份数据的两个出口。

| | 普通用户 | Geek |
|---|---|---|
| 是谁 | 用 Mac 工作、想让 AI 省掉重复交代背景的人。不懂也不想懂模型、MCP、提示词 | 已经在用 Claude Code、Codex 这类 agent，想让它读到自己上下文的人 |
| 入口 | Mac App | MCP、`candid` 命令、技能 |
| 第一次感到价值 | 装上、授权、过一天，打开就能回顾今天、搜到看过说过的东西、看到替他整理出来的日程和待办草稿 | 注册一个访问方，拿到 MCP 配置，问自己的 agent 一个跨来源的问题并得到带出处的回答 |
| 需要配置什么 | 尽量为零。默认设置就能用；模型来源有引导 | 自己选模型、范围、技能；可以脚本化 |
| 不能忍受什么 | 看不懂的设置页；不知道它在不在录；费电 | 数据锁在里面；接口不稳定；黑箱 |

两条约束由此而来：

1. **界面上能做到的，外部 agent 通过工具也应该能做到。** 反过来不要求：geek 能做的不必都有界面。
2. **默认值为普通用户设，开关为 geek 留。** 一个功能如果只有调过参数才能用，对普通用户等于不存在。

<a id="principles"></a>

## 4. 坚持什么

| # | 原则 | 落到产品上 |
|---|---|---|
| 1 | 本地优先 | 没有账号，没有我们的云，没有遥测，没有用户没配置的网络请求 |
| 2 | 采集可见 | 每次启动默认暂停；菜单栏始终显示在不在记录；可以按应用排除。没有你的知情就不记录、不发送 |
| 3 | 证据优先 | AI 的每条推断都能回到原始记录，都标明来源和模型，都能被纠正 |
| 4 | 开放可迁移 | 格式公开，数据能整体带走，不依赖 Candid 也能读 |
| 5 | AI 由你选 | 模型来源自己配，本地模型和云端 API 一视同仁；外部 agent 用同一套工具和权限 |
| 6 | 安静 | 不费电，不打扰。没事可报时不出声 |
| 7 | 简洁实用 | 界面少而准，不包装。宁可少一个功能，不要一个半成品 |

这些原则落到工程上的规则见[工程规范](engineering.md#principles)。

<a id="non-goals"></a>

## 5. 不做什么

| 不做 | 原因 |
|---|---|
| 云服务、账号体系、多人协作 | 与本地优先冲突 |
| 通用 agent 框架 | 对话与技能交给 Pi，外部 agent 走 MCP。自己造一套既做不好也不是要验证的问题 |
| 通用插件系统 | 扩展走三个接缝，见[架构总图](architecture.md#seams) |
| 替用户对外行动 | 发消息、改日历这类事只生成提案，用户批准后才执行 |
| 记忆与人格的默认设计 | 还在研究，见[研究记录](research/README.md)。先把数据理清，再谈让 AI「有记忆」 |
| 为演示效果做的功能 | 不追求在 GitHub 上好看，也不学大厂的个人 agent 那样包装 |

<a id="admission"></a>

## 6. 功能准入

加一个功能之前回答四个问题。答不上来就不做，或者先进[待办](roadmap.md)的「之后」。

1. **它属于第 2 节的哪一段？** 要么让数据更全、更干净，要么让 AI 的认知变成用户能感到的价值，要么让数据更带得走。三者都不沾的不做。
2. **两类用户各自怎么用到它？** 只服务一头的，要说明为什么值得。
3. **它带来多少后台开销，由什么触发？**
4. **它能不能由现有的三个接缝实现？** 能用技能做的不进核心；能用现有工具组合的不加新工具。

砍功能用同样的标准：一个已有功能如果答不出第 1 问，它是该删的候选。

<a id="measure"></a>

## 7. 怎么知道做对了（待定）

目前没有衡量「AI 是否更懂你」的固定办法。这是整个项目最该补的一块：没有它，第 2 节的问题永远没有答案，功能只会越加越多。

建议的最小做法，等主人确认：

| 步骤 | 内容 |
|---|---|
| 固定一组问题 | 十个左右关于你自己的问题，覆盖人、事、承诺、时间。例如：上周和某人聊了什么、答应了谁什么还没做、某个项目卡在哪、上周二下午在忙什么 |
| 每周跑一次 | 同一个模型，在「带 Candid 上下文」和「不带」两种情况下各答一遍 |
| 记三个数 | 答对率；引用的证据是否真实存在；每次问答的成本（调用次数和费用） |
| 看趋势 | 每个版本后这三个数往哪走。往回走的版本要找原因 |

基础已经有：`candid-lab` 能在真实数据的副本上重放整条流程并对比结果，见[研究记录](research/README.md)。

另外三个不需要新机制就能看的信号：

- 主人自己每天是否还在用，用的是哪个入口。
- 「理得清」的抽样正确率：随机抽若干条消息、人物、条目，人工判对错。
- 待处理的人物候选和条目草稿是被采纳得多，还是被忽略得多。

## 8. 还没定的方向

| 问题 | 现在的倾向 | 状态 |
|---|---|---|
| 平台顺序 | Mac 上先把第 2 节验证清楚，再做 Windows，最后手机。理由见[架构总图](architecture.md#platforms) | 待定 |
| 手机的角色 | 卫星：录音、照片、分享入口加查看，不做独立的采集与整理 | 待定 |
| 开放格式导出做成什么样 | 旧规格里有一张映射表，但依赖一份不在仓库里的封套格式定义 | 待定，见[契约清单](contracts/README.md) |
| 衡量办法 | 第 7 节的每周问答 | 待定 |
| 记忆与人格 | 只研究，不做默认设计 | 已定为不做，研究继续 |

这些问题在[待办](roadmap.md)的「等主人决定」里有对应条目。有了答案之后记进[决定流水](decisions/log.md)，并把本节对应的行改成已定的陈述。
