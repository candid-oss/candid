# 产品定位

这一页回答四个问题：Candid 是什么、为谁提供什么价值、不做什么、怎么知道做对了。方向只由仓库的主人改；其他文档和功能与本页冲突时，以本页为准。

标「待定」的条目是还没拍板的，不要当作既定方向去实现。

## 1. 一句话

Candid 是本地优先、开放、可迁移的个人上下文底座：把你在电脑上的一天整理成干净、有出处、可纠正的数据，交给你自己选择的 AI。

它同时是两样东西，共用同一份数据：

- **底座**：采集、整理、查询、权限与审计。这是产品本体。
- **自带界面**：一个薄的 Mac App，让不接任何外部 agent 的人也能直接得到价值。

## 2. 要验证的问题

**采集到的数据，能不能变成 AI 对一个人的认知？**

这是整个项目存在的理由。每个功能都应该能说清它在帮助回答这个问题的哪一段：

| 段 | 含义 | 现在对应的东西 |
|---|---|---|
| 采得到 | 该有的来源都进来了，而且不费电、不打扰 | 屏幕、截图、录音、邮件、日历、AI 会话 |
| 理得清 | 原始记录变成对话、消息、摘录、活动块、人物、条目 | 整理层与固定流程 |
| 用得上 | AI 拿到这些之后，回答和行动明显更懂你 | MCP 查询、技能、AI 页 |
| 带得走 | 数据是你的，能整体导出给别的工具 | 备份已有；开放格式导出未实现 |

## 3. 为谁，提供什么

| 用户 | 他得到什么 | 入口 |
|---|---|---|
| 普通用户 | 装上就能回顾一天、找到看过说过的东西、收到日程和待办草稿。不需要懂模型 | Mac App，默认配置可用 |
| Geek | 让自己的 agent（Claude Code、Codex 等）读到自己的上下文，可写技能、可脚本化 | MCP、`candid` 命令、技能 |
| 两者共同 | 数据只在本机，随时能看到在不在记录，随时能带走 | 菜单栏状态、备份、导出 |

两类用户不是两套功能，而是同一份数据的两个出口。界面上的每个功能，外部 agent 也应该能通过工具做到；反过来不要求。

## 4. 原则

1. **本地优先。** 没有账号，没有我们的云，没有遥测，没有用户没配置的网络请求。
2. **采集可见。** 没有你的知情就不记录、不发送。
3. **证据优先。** AI 的每条推断都能回到原始记录，都能被纠正。
4. **开放可迁移。** 格式公开，数据能整体带走。这一条是 Candid 和系统厂商自带 AI 的根本区别，不能只停在口号上。
5. **简洁实用。** 界面少而准，不包装。宁可少一个功能，不要一个半成品。

## 5. 不做什么

- 不做云服务，不做账号体系。
- 不做通用 agent 框架。对话与技能交给 Pi，外部 agent 走 MCP。
- 不做通用插件系统。扩展走三个接缝，见[架构总图](architecture.md#seams)。
- 不为了演示效果做功能。不追求在 GitHub 上好看。
- 记忆与人格不做默认设计，只作为研究议题（见 [Agent 基座 §6](specs/agent-platform-v1.md)）。

## 6. 功能准入

加一个功能之前回答三个问题，答不上来就不做：

1. 它属于第 2 节的哪一段？
2. 普通用户和 geek 各自怎么用到它？只服务一头的要说明为什么值得。
3. 它带来的后台开销是多少，谁触发？

## 7. 怎么知道做对了（待定）

目前没有衡量「AI 是否更懂你」的固定办法，这是最该补的一块。建议的最小做法，等主人确认：

- 固定一组关于你自己的问题（例如十个：上周和谁聊了什么、答应了谁什么、某个项目卡在哪）。
- 每周让同一个模型在「带 Candid 上下文」和「不带」两种情况下各答一遍，人工判对错。
- 记录三个数：答对率、引用的证据是否真实、每次问答的成本。

数据层的对照实验工具（`candid-lab`）已经能在真实数据的副本上重放流程，可以作为这件事的基础。

## 8. 平台顺序（待定）

建议的顺序：Mac 上先把第 2 节的问题验证清楚，再做 Windows 采集端，最后才是手机。理由和前提见[架构总图](architecture.md#platforms)。
