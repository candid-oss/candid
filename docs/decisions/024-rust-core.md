# ADR-024：跨平台 Rust 核心

**中文** · [English](024-rust-core.en.md)

状态：已决定。M1 已实现并验证；M2（App 切换到 Rust 核心）已实现并通过性能验收；M3 的 AI 会话文件连接器已迁入 Rust；其他 M3 工作按功能推进。时间线库的表结构、接口和权限规则（[时间线库 v1](../specs/timeline-v1.md)）与本决定无关。

## 背景

Mac 版的核心代码（时间线库、查询服务、连接器、模型调用）都用 Swift 写成，并越来越多地依赖苹果框架（CryptoKit、钥匙串、Network、EventKit）。用户希望以后做 Windows 版，并接受采集和权限在 Windows 上重做；安卓本来就是已选定的方向。

接下来要写的大块核心代码，包括数据整理流程、邮件连接器、任务机制（见[个人 Agent 基座 v1](../specs/agent-platform-v1.md)），如果继续用 Swift 写，以后跨平台时还要再写一遍。用户认为「核心用 Swift、界面用 Windows 原生」太别扭，倾向于跨平台核心。

## 候选

| 候选 | 好处 | 代价或问题 |
|---|---|---|
| 核心继续用 Swift，Windows 上也用 Swift 编译核心 | 不用重写 | Swift 在 Windows 上的生态和工具链薄弱；苹果框架都要另找替代；安卓无法共用 |
| Rust 核心，各平台原生界面（本决定） | 一份核心覆盖 Mac、Windows、Linux、安卓；桌面端以独立进程提供接口，任何前端都能直接调用；SQLite、HTTP、MCP、MIME 解析、邮件同步、密钥存储都有成熟的库；内存释放确定，没有引用计数和垃圾回收开销 | 要重写约 7,500 行 Swift 核心代码及测试；多一个辅助进程要管理（实测空闲约 9 MB）；构建链多一步 |
| Kotlin Multiplatform 核心 | 安卓最自然 | Mac 和 Windows 上的运行时和互操作较重，邮件、SQLite 等底层库不如 Rust 成熟 |
| 全部改成 Tauri（Rust 核心 + 网页界面） | 界面也只写一份 | Mac 界面失去原生质感，和现有设计规范冲突；系统采集仍要写原生插件 |
| C++ 核心 | 跨平台 | 内存安全和依赖管理成本高，没有优势 |

## 选择

### 1. 三个部分

| 部分 | 内容 | 实现 |
|---|---|---|
| **Rust 核心** | 时间线库、查询工具、权限和审计；本机 HTTP、MCP 服务和命令行；数据整理；固定流程调度；模型调用和用量；设置；**所有读文件或走网络的连接器**（系统「邮件」App 和 Thunderbird 的本机数据、IMAP、浏览器历史、AI 对话记录、笔记目录） | 一个 Rust 库，所有平台共用；另编一个不带界面的命令行版本，可在 NAS 或 Linux 上单独运行 |
| **平台前端** | 界面 | Mac 用 SwiftUI，安卓用 Kotlin，Windows 以后在 Tauri 和 WinUI 中选 |
| **系统接入** | 必须调用系统接口或由 App 申请系统权限的部分：屏幕和应用采集、权限申请与引导、系统日历和提醒、MailKit 实时邮件扩展、通知、菜单栏、小组件 | 各平台各写一份，和前端在同一个进程 |

连接器的归属规则：**读文件、走网络的放核心；调系统接口的放平台层。**

2026-11-12 用户决定：Mac 软件本体仅用 Swift + Rust，不依赖 Python。转写、声纹及其他模型统一作为外部服务，Rust 调接口并校验结果；不启动 Python worker、不管理模型环境。外部服务可本机部署，语言不限，开发/测试/硬件调试脚本不属于产品运行依赖。当前 Hub 仍拥有媒体库和语音队列，需按架构中的单一负责人规则逐步迁移；设备经 Hub 或 App 接入；外部 agent 经 MCP 或命令行访问。

### 2. 边界规则

- **目标是只有核心打开产品数据库。** 当前 Hub 媒体库仍独立，迁移前由 Hub 独占； 前端和系统接入不直接读写 SQLite。
- **写入只有一个入口。** 所有连接器，不管在核心还是平台层，都通过核心的入库接口写入，经过同样的打码、去重和筛选。
- **读取只有一套接口。** 前端、MCP、命令行、内置任务用同一组查询工具，权限过滤和审计也是同一套。
- **密钥由核心统一读写**（Mac 用钥匙串，Windows 用凭据管理器）；**系统权限由平台层申请**，因为系统按 App 授权。
- **核心不依赖任何平台的界面框架。** 需要平台能力的地方定义成接口，由平台层实现后注入。

### 3. 代码布局与进程边界

- 核心放在 `core/`，一个 Cargo workspace。首批 crate：
  - `candid-store`：表结构、入库、查询工具、访问方与审计；
  - `candid-service`：回环 HTTP 与 MCP；
  - `candid-cli`：`candid` 命令，含不带界面的服务模式 `candid serve`。
  
  模型、整理和固定流程优先放入现有 store/service 的模块；有独立依赖需要时再拆 crate。
- **桌面端用独立进程，不做进程内绑定**。核心以 `candid serve` 作为 App 包里的辅助进程运行（`Contents/Helpers/candid`，签名随 App），由 App 启动、监控，异常退出后重启。界面、采集、MCP、命令行和外部 agent 都通过同一套本机接口访问核心，不引入 uniffi 等绑定生成工具。
  - App 与核心之间用只有当前用户能访问的本地通道（Unix 域套接字；Windows 用命名管道），外部访问方继续用带令牌的回环 HTTP。两者是同一套工具和同一套权限、审计。
  - 桌面端在 M1 已有的查询工具之外补三样：App 自用的入库接口（采集写入）、「有新数据」的推送通道（界面刷新）、核心进程的健康检查。
  - 调用只传分页后的结果和文件路径，不传截图、录音这类大块字节。
  - 需要「完全磁盘访问」的读取（如系统「邮件」App 的数据）由核心进程执行。App 启动的辅助进程通常按 App 归属权限，接入邮件前实测确认。
- **安卓以后再定**：手机上不适合常驻辅助进程，届时在进程内调用（uniffi 或手写薄 JNI）中选择。
- 核心内部的异步运行时限制在一两个工作线程。

### 4. 迁移步骤

| 步骤 | 内容 | 验收 |
|---|---|---|
| M1 时间线库与服务 | Rust 实现 `candid-store`、`-service`、`-cli`；表结构与 Swift 版完全一致，同一个数据库文件两边都能打开；测试用同一批合成样例 | 现有时间线库、查询服务和服务端测试的场景全部移植并通过；在真实库的副本上，两边命令行对同样的查询给出相同结果（只报计数和差异条数） |
| M2 App 切换 | App 启动并管理 `candid serve` 辅助进程，界面和采集改为经本地通道调用核心；删除 Swift 版的时间线库、查询接口、服务和命令行；界面不变 | 下文的性能条件全部满足；现有界面自检与测试通过 |
| M3 新功能进 Rust | 模型服务调用和用量、文件类连接器、数据整理、任务机制及 Python Hub 的产品职责迁入 Rust；邮件后续 | 各自按对应规格验收；无 Python 环境时采集/保存/导入/播放/搜索/MCP 可用，获准模型服务可接通，断开服务只影响处理；无 Python 子进程 |

**性能验收**（M2 切换前必须满足，用同一份数据、同一台机器对比 Swift 版）：

- 空闲内存不高于 Swift 版（当前约 77 MB）；
- 首次同步真实规模的库时的内存峰值不高于 Swift 版；
- 典型查询延迟不高于 Swift 版（当前 `overview` 约 60 ms）；
- App 体积增加不超过 15 MB。

### 5. 对现有待办的影响

- 删除回放、交互色改为系统强调色：照常进行，与核心无关。
- 时间线界面改读时间线库：先定义界面使用的读取接口，现在由 Swift 版实现，M2 时换成 Rust 版。已实现：读取接口为核心的 `app_*` 工具，采集也已直写核心。
- 采集直接写时间线库、AI 用量写入 `ai_calls`：放到 M1 之后，直接在 Rust 核心上做，避免写两遍。
- M1 期间 Swift 核心只修缺陷，不加新功能。

## 代价与可逆性

- **重写成本**：约 7,500 行 Swift 核心代码和对应测试。界面（约 11,000 行）和桌面采集不动。
- **工程复杂度**：两种语言、辅助进程的启动和监控、通用二进制和签名；崩溃报告需要保留 Rust 的调试符号；跨语言的问题更难排查。
- **数据兼容**：表结构和数据根目录布局由时间线库规格规定，与实现语言无关。M2 之前随时可以退回 Swift 版，数据不需要转换。
- **Windows 界面**未定；本决定只保证核心和接口可以共用。
