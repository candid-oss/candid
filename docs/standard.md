# 文档规范

**状态**：已生效（2026-11-26 起）。旧规格已按本规范拆分，对照见[规格索引](specs/README.md#legacy)。

本文规定这个仓库里每一份文档放在哪、必须有什么、不能有什么、怎么互相引用、怎么保持为真。
它不规定代码怎么写（见[工程规范](engineering.md)），也不规定产品做什么（见[产品定位](product.md)）。

写文档和清理文档时都以本文为准。本文与某份文档的现状不一致时，改那份文档。

<a id="why"></a>

## 1. 为什么要有这份规范

仓库的主人只做上层设计，不读代码。主人对系统的控制完全通过文档和测试实现，所以文档必须满足三件事：

1. **找得到。** 一个问题只有一个该去的地方，从索引两步以内能到。
2. **信得过。** 文档里的每句话要么现在为真，要么明确标出它不是（未实现、未验证、已废弃）。
3. **不丢东西。** 讨论过的决定、做过的实验、放弃的方案都留有记录，但不和现行规则混在一起。

过去的问题正是这三条的反面：规格里混着决定、进度、日期流水和实验数据，一份文档七万字，没人能判断哪句还算数。

## 3. 文档种类

每一种回答一类问题。内容跨两类时拆成两份，用链接连起来。

| 种类 | 位置 | 回答的问题 | 谁能改 | 寿命 |
|---|---|---|---|---|
| 定位 | `product.md` | 做什么、不做什么、为谁 | 主人拍板后才改 | 长期 |
| 地图 | `architecture.md` | 系统有哪几块、谁依赖谁、往哪扩展、欠着什么 | 结构变了才改，需有决定记录 | 长期 |
| 规范 | `engineering.md`、`standard.md` | 所有改动都要守的规则 | 需有决定记录 | 长期 |
| 术语 | `glossary.md` | 一个词在这个项目里指什么 | 随规格改 | 长期 |
| 契约 | `contracts/` | 哪些对外承诺不能悄悄改，谁守着 | 改契约的改动同时改 | 长期 |
| 规格 | `specs/` | 一个主题**现在**的行为和规则 | 改行为的改动同时改 | 随代码 |
| 决定 | `decisions/` | 为什么这么定，当时还考虑过什么 | 只追加，不改写 | 永久 |
| 计划 | `plans/` | 一件正在做的事：目标、步骤、进度 | 做这件事的人 | 做完即删 |
| 研究与实验 | `research/` | 一次调研或实验看到了什么 | 只追加，不改写 | 永久 |
| 版本记录 | `changelog.md` | 每个版本做了什么 | 每次合并时追加 | 永久 |
| 待办 | `roadmap.md` | 下一版和之后要做什么，什么在等主人决定 | 随讨论改 | 长期 |
| 模块说明 | 各目录 `README.md` | 这一块怎么构建、运行、测试 | 改构建方式的改动同时改 | 随代码 |

### 3.1 各种类的必备内容与禁止内容

| 种类 | 必须有 | 不能有 |
|---|---|---|
| 规格 | 第 4 节的文件头；第 5 节的固定章节 | 进度流水、带日期的「某日已做」、实验数据、被否决的方案的展开讨论、「下一步」 |
| 决策记录 | 背景、考虑过的选项、决定、代价、影响到的文档 | 之后的修改（新决定写新的一条，旧的标「被 NNN 取代」） |
| 决定流水 | 日期、决定的一句话、落在哪份文档 | 长篇论证（论证长就升格成决策记录） |
| 计划 | 目标、不做什么、步骤与进度、待主人决定的问题、完成后结论并入哪里 | 长期规则（规则写进规格，计划里只链接） |
| 研究与实验 | 日期、问题、方法、数据或观察、结论、结论被哪份规格或决定采用 | 现行规则 |
| 版本记录 | 版本号、日期、按用户能感知的变化分组的条目 | 实现细节、文件名清单 |
| 待办 | 每项的来源链接、状态、属于哪个版本 | 已完成的项（完成后移到版本记录） |

## 4. 文件头与状态用语

每份规格、计划、研究记录、决策记录都以这个文件头开始：

```markdown
# 标题

**中文** · [English](x.en.md)            ← 只有双语文档有这一行

**状态**：<状态用语>。<一句话补充，可省>

<范围：一到三句话。这份文档回答什么；不回答什么，那些去哪看。>
```

状态行只有一句。进度写在计划里，历史写在版本记录里。

### 4.1 状态用语

整份文档和文档里的单条断言都只用这几个词，不自造：

| 用语 | 含义 | 判断依据 |
|---|---|---|
| 已实现 | 代码里有，且有测试覆盖 | 能指出实现文件和测试 |
| 部分实现 | 一部分有，一部分没有 | 文中逐项标明 |
| 未实现 | 设计已定，代码里没有 | 在代码里找不到 |
| 设计中 | 还没定 | |
| 已废弃 | 曾经有，现在不用 | 写明被什么取代 |
| 未验证 | 文档这么写，但没有核对过代码或没有测试支撑 | 写的人没有去查，或查不到 |

规则：**不确定就标「未验证」，不要猜成「已实现」。** 标了「未验证」的句子，下一个读到并核对了的人负责改成确定的状态。

规格正文默认描述已实现的行为，所以已实现的不用逐句标。只标例外：在句末或表格的状态列写 `（未实现）`、`（未验证）`、`（已废弃）`。

## 5. 规格怎么写

### 5.1 一份规格一个主题

规格按**主题**分，不按写作时间或项目阶段分。主题就是[架构总图](architecture.md)里能指出来的一块能力，例如存储、整理层、查询接口、连接器。

文件名用主题的英文短名，不带版本号：`specs/storage.md`。版本由[版本记录](changelog.md)和 git 负责，不靠文件名。

### 5.2 固定章节

```markdown
## 1. 概览
这一块是什么、在系统里处于什么位置、和哪几块相邻。一段话加一张表或一张图。

## 2 … N. 正文
按子主题分节。每节一个稳定锚点。

## N+1. 实现位置
| 内容 | 代码 | 测试 |
列出主要模块文件和守护它的测试文件，让人能从规格走到代码。

## N+2. 未实现与待定
| 项 | 状态 | 说明 | 待办链接 |
设计已定但没做的、还没定的、标了未验证的，集中列在这里。每项在 roadmap.md 有对应条目。

## N+3. 来源
这份规格的内容从哪些旧文档的哪些章节迁来，或由哪条决定产生。只列链接，不叙述。
```

### 5.3 长度

- 一份规格以两万字符为上限（约三百行正文）。超过就按子主题拆成两份，并在规格索引里相邻列出。
- 一节超过一屏半时，考虑拆小节或改成表格。
- 细到字段级的清单（表结构、payload 字段、工具参数）放在该规格末尾的附录小节，或直接指向代码和快照文件，不在正文里铺开。能由代码或快照生成的清单，以代码和快照为准，文档只留说明和链接。

### 5.4 写法

- 用陈述句写规则：「一个批次在一次事务里完成」，不写「我们决定」「后来改成」。
- 先写规则，再写原因，原因一两句。原因很长说明它是一条决定，写进决定流水并链接过去。
- 同一件事只在一份规格里写。别的规格需要提到时写一句话加链接。
- 阈值、默认值、枚举写具体的值，并注明它存在哪里（配置键、常量、表）。
- 每个专有名词第一次出现时链接到[术语表](glossary.md)，全文用同一个词。
- 例子用合成数据。

<a id="history"></a>

## 6. 记录信息怎么保留

清理文档时**不丢信息，只挪位置**。旧文档里的每一段都属于下面某一类，去到对应的地方：

| 旧文档里的内容 | 去哪 | 怎么写 |
|---|---|---|
| 现在仍然成立的规则和行为 | 对应主题的规格 | 按第 5 节重写为陈述句，保留原有的表格、字段、阈值 |
| 「某日决定……」「设计决定：……」 | `decisions/log.md` | 一行：日期、决定、落在哪份规格。原文的理由保留为一两句 |
| 影响结构、难以反悔的决定 | `decisions/NNN-*.md` | 完整的决策记录 |
| 「某日已实现……」、实施切片、里程碑进度 | `changelog.md` 对应版本 | 改写成用户能感知的变化；内部细节保留为该条目下的一行 |
| 实测数据、对照实验、调研结论、竞品参考 | `research/` | 原样保留数据和结论，补上日期和问题 |
| 「待定」「待验证」「下一步」「不在这一版」 | `roadmap.md`，并在对应规格的「未实现与待定」里留一行 | |
| 已经不成立的规则、被取代的设计 | 决定流水里记一行「某设计被某取代」 | 规格里不保留正文 |
| 旧数据迁移步骤（已完成的一次性工作） | `changelog.md` 的对应版本，细节放 `research/` 或直接删去并在决定流水记一行 | |

### 6.1 搬迁对照表

旧文档被拆分后，原文件**不删除**，改成一页搬迁对照表：旧章节号和旧锚点各去了哪里。原因是代码注释里有上百处按章节号引用旧文档（例如 `agent-platform-v1 §2.6`），这些引用要能继续查到。

对照表文件的状态行写「已废弃：内容已迁出，本页只保留对照表」。对照表不再接受新内容。

<a id="links"></a>

## 7. 引用规则

1. **文档之间**用相对链接，指到锚点：`[入库协议](specs/connectors.md#ingest-protocol)`。链接必须指向存在的文件。
2. **锚点**是手写的稳定标识：在标题上一行写 `<a id="ingest-protocol"></a>`，小写英文加连字符。标题文字可以改，锚点不改。每个二级标题和被外部引用的三级标题都要有锚点。
3. **不用章节号引用别的文档。** 章节号会随编排变化。写 `specs/storage.md#events`，不写「存储 §4.2」。同一份文档内部可以用「第 3 节」。
4. **代码注释引用文档**时写路径加锚点：`// See docs/specs/storage.md#events`。旧注释里的章节号引用不强制改，经搬迁对照表查；碰到相关代码时顺手改成新写法。
5. **不引用仓库里没有的文档。** 需要的内容补进仓库，或删掉这句引用。
6. **文档引用代码**时写到文件，不写行号。

<a id="language"></a>

## 8. 语言

| 文档 | 语言 |
|---|---|
| 仓库 README、CONTRIBUTING、SECURITY、各模块 README | 中英文 |
| 规格、决策记录 | 中英文两个文件：`x.md`（中文，为准）与 `x.en.md` |
| 定位、地图、规范、术语、契约清单、决定流水、计划、研究与实验、版本记录、待办 | 只写中文 |

- 双语文档以中文为准。改动先改中文，再让英文与之一致；两版的章节和锚点必须相同。
- 英文版允许比中文晚一步，但不能晚过一次合并：合并进主分支时两版必须一致。
- 面向主人的文字说人话：先给结论，再给依据；不贴代码，不用内部代号。

## 9. 版本记录与待办

主人和 agent 讨论出来的东西，按下面的路径留痕。每一步都有固定的落点，讨论本身不留在聊天记录里。

```
讨论 ──► 决定流水（当天记一行）
          │
          ├─► 待办 roadmap.md（要做，排进某个版本或留在「之后」）
          │        │
          │        └─► 计划 plans/（开始做时才写，小事不用写）
          │                 │
          │                 └─► 实现 ──► 规格 / 契约 / 地图 同步更新
          │                                   │
          │                                   └─► 版本记录 changelog.md（合并时记一条）
          │                                        待办里对应项删除
          └─► 不做（在决定流水里写明不做和理由）
```

### 9.1 版本号

- 版本号是 `主.次.修`，与 `core/Cargo.toml` 的 `version` 和发布标签 `vX.Y.Z` 一致。
- 1.0 之前：次版本号对应一轮有主题的工作（主人能说出「这一版是做什么的」）；修订号对应只修问题的发布。
- 表结构版本（`SCHEMA_VERSION`）是另一个数，记在每个版本条目里，不和产品版本号混用。

### 9.2 `changelog.md` 的格式

最新的在最上面。最上面永远是「未发布」，合并进主分支的改动先记在这里，发布时改成版本号和日期。

```markdown
## 未发布

**主题**：这一版要解决什么（一句话）。

### 新增
- 用户能感知的变化，一句话。（[规格](specs/x.md#anchor)）

### 改变
### 修复
### 内部
- 用户感知不到、但后续开发需要知道的变化：表结构版本、契约变化、文档结构调整。

## 0.1.0 · 2026-11-18
```

规则：每条写用户或后续开发者关心的结果，不写做了哪些文件。改了契约的必须在「内部」里写明。

### 9.3 `roadmap.md` 的格式

```markdown
## 下一版：0.x — <主题>
| 项 | 状态 | 来源 | 说明 |
状态只用：待开始 / 进行中 / 待验证 / 搁置

## 之后
按主题分组的候选项，不排期。

## 等主人决定
| 问题 | 选项 | 建议 | 提出日期 | 影响哪些项 |

## 已知问题
发现了但没排期的缺陷和欠账，带来源链接。
```

规则：每项都有来源（规格的「未实现与待定」、一条决定、一次实验）。完成的项从待办删除并记进版本记录。「等主人决定」里的问题一旦有答案，记进决定流水并从这里删除。

### 9.4 `decisions/log.md` 的格式

```markdown
| 日期 | 决定 | 理由（一两句） | 落在 |
```

最新的在最上面。一条决定只占一行；理由写不下就升格为决策记录，流水里留链接。被推翻的决定不删，在新的一行写「取代某日某条」。

## 10. 保持为真

### 10.1 改代码时

| 改了什么 | 同时改 |
|---|---|
| 一个主题的行为 | 该主题的规格；如果让某条「未实现」变成了「已实现」，改掉状态并删掉待办里的对应项 |
| 对外接口、输出字段、协议、表结构 | 契约清单与快照 |
| 模块边界、依赖方向、新增接缝 | 架构总图，并记一条决定 |
| 构建、运行、测试方式 | 模块 README、AGENTS.md、`scripts/check.sh` |
| 新增存储位置 | 数据位置与迁移 |
| 任何合并进主分支的改动 | 版本记录的「未发布」加一条 |

不同步的改动不算完成，见[工程规范](engineering.md)的「完成的定义」。

### 10.2 自动检查

```bash
python3 scripts/check_docs.py
```

它检查：相对链接指向存在的文件；规格与决策记录中英文成对；每份规格、决策记录、研究记录都列在所在目录的索引里；规格没有超过长度上限；规格具备文件头的状态行。CI 上每次推送都跑。

### 10.3 人工检查清单

写完或审一份规格时逐条过：

- [ ] 状态行只有一句，用的是第 4.1 节的词。
- [ ] 范围段说清了回答什么、不回答什么。
- [ ] 正文没有日期流水、进度、实验数据、「下一步」。
- [ ] 每条未实现或未验证的内容都标了，并列在「未实现与待定」里。
- [ ] 「实现位置」里的文件确实存在。
- [ ] 没有用章节号引用别的文档；没有引用仓库里不存在的文档。
- [ ] 专有名词与术语表一致。
- [ ] 长度在上限以内。
- [ ] 英文版结构与中文版一致。
