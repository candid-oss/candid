# 个人 Agent 基座 v1：数据整理、功能取舍与任务机制

**状态**：用户决定 AI 功能分两种：核心内自动的简单功能，和挂接的 Pi（AI 页对话或钩子启动，用我们的技能、插件与护栏）；另提供 MCP/API 给外部 agent（第 4.1 节）；第 4 节最小固定框架已有实现与隔离验证；邮件（本机邮件 App + IMAP）与浏览器历史（导入关闭）连接器已在 Rust 核心实现并以合成样例验证，时间线库升为 v4；其余能力按任务表放行。

与其他规格的分工：

- 存储、查询工具、访问方与用量表：[时间线库 v1](timeline-v1.md)。
- 音频流水线、模型角色与按任务选模型：智能处理。
- 派生对象的身份、修订与 ContextPack：artifact v1。
- 工具权限、提案与会话规则：[Agent 模块](../../agents/README.md#tool-policy)。

核心与平台的分工见 [ADR-024](../decisions/024-rust-core.md)：本文的整理流程、连接器（系统接口类除外）、任务和执行者都在 Rust 核心里实现。

本文只维护三件事：数据从哪来、怎样整理干净（第 2 节）、哪些功能自己做（第 3 节）、AI 功能怎样定义和执行（第 4、5 节）。记忆与人格不在本文给默认设计，只列研究议题（第 6 节）。

<a id="position"></a>

## 1. 定位与原则

Candid 同时是两样东西：

- **独立产品**：不接任何外部 agent，也能完成浏览、搜索、简单回顾与待办草稿。
- **个人 agent 基座**：把采集到的信息整理成干净、可引用、可纠正的数据，供 Claude Code、Codex、OpenClaw、pi、DeepSeek Harness 等外部 agent 读取。

> 设计决定：关键问题是「数据怎样处理干净」和「哪些功能做、哪些不做、哪些只做模板交给外部 agent」；任务定义与执行者分开；记忆和人格单独研究，不做默认设计。

原则：

1. **内置能力和外部 agent 读同一份数据**，都经过时间线服务的范围过滤与审计。
2. **花钱按层递增**：规则、统计不花 token；小模型按「段」调用一次并缓存；固定流程只在获准触发时运行，有预算上限。
3. **合并只建关联，不删原件**。去重、降噪、实体合并都记录为关系或权重，可以撤销和重算。
4. **写操作只走提案**；派生草案可以在授权范围内自动保存，但始终标明是草案。
5. **屏幕、网页、消息、邮件里的文字都是不可信数据**：可以作为证据，不能作为指令。任务提示词把它们放在明确的数据区，执行者不带终端和文件写入工具。

## 2. 数据整理流程

> 采集信号怎样先变成「访问、输入、阅读增量、关键帧」等原始记录单位，见原始记录层 v1。本节的整理流程在那些记录之上运行。

桌面文字、资料库的转写和连接器内容都走下面的流程；音频本身的转写、说话人和相关性初筛仍按智能处理。

| # | 环节 | 产出 | 用模型 | 现状 |
|---|---|---|---|---|
| 1 | 入口过滤与打码 | 被排除的应用和窗口不入库；密钥类文本入库前替换 | 否 | 排除已有（桌面采集 v1）；打码缺 |
| 2 | 规范化与切分 | 段落 | 否 | 已有（[时间线库 §4.6](timeline-v1.md)） |
| 3 | 精确去重 | 同一段文字全库一份 | 否 | 已有 |
| 4 | 近似去重 | 段落族 | 否 | 缺 |
| 5 | 降噪 | 每个段落族的「界面固定文字」权重 | 否 | 缺 |
| 6 | 分段 | 活动段、片段 | 片段标题用小模型 | 活动段已有；片段只有表结构 |
| 7 | 抽取 | 带证据的候选：人、项目、承诺、决定、话题 | 小模型，每段一次 | 只有 `memories` 表结构 |
| 8 | 实体归一 | 实体、别名、提及 | 规则为主，模糊时小模型 | 缺 |
| 9 | 召回 | 带证据、已折叠的结果 | 否（向量可选） | 全文检索已有；短词、折叠、实体扩展缺 |
| 10 | 汇总 | 小时、天、周的精简摘要 | 小模型 | 缺 |

### 2.0 来源覆盖：更多连接器

> 设计决定：要做更多连接器，例如邮件，这些对收集信息很重要。

承诺、请求、人和项目大多出现在邮件和消息里，只靠屏幕采集会漏掉没打开过的内容，也拿不到完整的线程结构。所以这类来源应作为**采集型**连接器：正文入库，进入下面的去重、实体、抽取流程。附件、远端文档这类体积大或变化快的内容仍按引用处理，用时到源头现读。

> 设计决定：邮件保留读本机「邮件」App 为主路线，**另加** himalaya 背后 Rust 库（pimalaya / email-lib）的 IMAP 登录适配器；浏览器历史连接器现在就做，但**先不导入**。

连接器清单（顺序、来源、映射、默认策略和实现状态）已移到[时间线库 §6.3](timeline-v1.md#connector-table)，只在那里维护。

所有新连接器都遵守：

- 每个连接器、每个账号单独授权，可以随时撤销；撤销后不再读取，已入库内容按你的选择保留或删除。
- 别人发给你的内容同样经过入口打码（2.1）；对外部访问方默认只给元数据，正文需要单独的范围。当前实现（工程选择）：邮件正文入库前做密钥样式屏蔽（与 AI 会话相同的规则，2.1 的卡号等其余规则未做）；邮件来源 `agent_visible=false`，外部访问方默认整条看不到，须在其范围里按来源 ID 授予——「只给元数据」的分级视图尚未实现。
- 按[时间线库 §6.1](timeline-v1.md)的采集型协议实现，用合成样例测正常同步、重复同步、中断重试、格式未知时拒绝和撤销授权。

<a id="mail"></a>

#### 2.0.1 邮件连接器

> 设计决定：邮件连接器由 Candid 自己实现，主路线读取本机「邮件」App 的数据；不依赖第三方邮件 MCP 工具，也不为每家邮箱分别实现登录。
>
> 设计决定：在主路线之外加 himalaya（pimalaya / email-lib）的 IMAP 登录适配器，Gmail 先走应用专用密码。

**实现状态**：Rust 核心 `candid-connectors` 已实现共用流程和两个适配器——本机「邮件」App（适配器 1）与 IMAP（适配器 3）；只用合成样例和本机假 IMAP 服务验证，真实邮箱只读试运行、Thunderbird 适配器、MailKit 扩展和 OAuth 登录未做。运行与接口见[核心运行说明](../../core/README.md#mail-browser-connectors)。

**为什么这样选**：

参考资料：[EagleFiler 导入邮件](https://c-command.com/eaglefiler/help/importing-mail-from-app)、[DEVONthink 与完全磁盘访问](https://www.devontechnologies.com/support/faq/full-disk-access)、[EmailEngine 文档](https://learn.emailengine.app/docs)、[Littlebird 连接工具](https://docs.littlebird.ai/learn/connect-your-tools/)、[claude-connector-apple-mail](https://github.com/falconbradley/claude-connector-apple-mail)、[MailKit MEMessageActionHandler](https://developer.apple.com/documentation/mailkit/memessageactionhandler)。


- 各家分别接官方接口，要分别注册 OAuth 应用；读邮件权限审核严，公司的 Microsoft 365 常常禁止第三方应用。云端助手类产品（如 Littlebird）也只接了两三家。
- 统一邮件接口服务（Nylas、EmailEngine）只是把各家的差异藏在服务后面，仍要自己注册 OAuth 应用，而且是云服务或付费的自部署服务，和本地、独立运行的目标冲突。
- Mac 本地归档工具（EagleFiler、DEVONthink）走的是「读邮件 App 的本机文件 + 完全磁盘访问」；依赖邮件 App 插件的做法已被苹果废弃。
- 社区的 Apple Mail MCP 项目（如 claude-connector-apple-mail、apple-mail-mcp）面向 agent 临时查询，只提供搜索和读取，没有增量同步、删除检测和线程。它们以 Python 或 Node 运行，完全磁盘访问只能授给解释器或终端，范围过大。只把它们当作表结构和文件格式的参考，借鉴前先看许可证，不复制代码。
- 邮件入库后，外部 agent 经 Candid 自己的 MCP 就能查到，带范围过滤和审计，不需要另接邮件 MCP。

**数据来源**：

- 索引：`~/Library/Mail/V<n>/MailData/Envelope Index`（SQLite）。以只读、不改动的方式打开，运行时识别表结构，只认已验证过的版本；认不出就整体拒绝并在连接页提示，不按猜测读取。
- 正文：各邮箱目录下的 `.emlx` 文件，结构是首行字节数、RFC 822 原文、末尾的属性表。`.partial.emlx` 只下载了一部分，按已有内容入库并标记为不完整；邮件 App 没下载的正文不读取，也不触发下载。
- 权限：需要你给 Candid 开「完全磁盘访问」。没有权限时连接器显示为未授权，不重试、不报错刷屏。

**同步**：

- 以索引里的邮件行号和修改信息作为游标，增量读取新邮件。
- 每轮比对已入库邮件是否还在，删除和移动记为墓碑或新修订，不静默丢失。实现：只剩在废纸篓/垃圾邮件里或已彻底删除的邮件按 `source_deleted` 删除并留墓碑（之后从废纸篓恢复也不会再入库）；换邮箱（如归档）是同一事件的 payload 修订。
- 邮件 App 没下载正文的邮件按索引里的主题、发件人和时间只存元数据（`body_status=not_downloaded`），之后下载了也不自动补正文（待定）。
- `source_key` 用 Message-ID；没有 Message-ID 时用账户、邮箱和行号组合。同一封邮件出现在多个邮箱（收件箱和归档）时只入库一次，记录它所在的邮箱。
- 只读：不改标记、不移动、不删除，也不调用邮件 App 的脚本接口。

**解析**：

- MIME：多段结构；quoted-printable 和 base64；邮件头里的编码文字（RFC 2047）；字符集用系统转换，至少覆盖 UTF-8、GBK、GB2312、GB18030、Big5、ISO-2022-JP、ISO-8859 系列和 Windows 代码页。
- 正文优先取纯文本部分；只有 HTML 时转成纯文本，去掉样式、脚本和跟踪图片。
- 引用的历史回复和签名单独标出，不进入抽取输入；它们本来就在线程里更早的邮件中，通过段落去重自然折叠。实现：存入独立文字字段 `quoted`（时间线库 v4），`body` 只放新写的部分。
- 附件只记文件名、类型和大小；需要内容时按引用现读，同样受访问范围约束。

**事件映射**：每封邮件一个 `mail.message` 事件，正文字段 `body`、主题 `subject`；线程按 Message-ID、In-Reply-To 和 References 组成 `mail_thread`。具体 payload 落地时写进[时间线库 §4.3](timeline-v1.md)。

**存储适配器**：

邮件连接器在 Rust 核心里实现（[ADR-024](../decisions/024-rust-core.md)）。解析、组线程、清洗、筛选和 AI 判断只有一份；「从哪里读邮件」做成可替换的适配器：

| 顺序 | 适配器 | 平台 | 说明 |
|---|---|---|---|
| 1 | 系统「邮件」App 本机数据 | Mac | 上文的主路线；**已实现**，只认 `V10` 且索引表结构与合成签名一致，其他版本整体拒绝（`unknown_mail_version` / `unknown_mail_schema`），真实版本待只读试运行确认 |
| 2 | Thunderbird 本机数据 | Mac、Windows、Linux | Thunderbird 自己处理 Gmail、Outlook 的 OAuth 登录；145 版（2025 年 11 月）起原生支持 Exchange 邮件，走的是微软正在淘汰的 EWS 接口，有报道称 2026 年 10 月起 Exchange Online 停止第三方 EWS 访问，接入前核实。需要在 Thunderbird 里保留离线副本；本机存储格式（mbox 或 Maildir）实测后确定 |
| 3 | 自己登录（IMAP） | 全部 | **已实现**：email-lib 0.27 只用 EXAMINE、UID SEARCH、BODY.PEEK 读取，不改标记、不移动；邮箱移出后按 Message-ID 在其他文件夹（如 Gmail「所有邮件」）查找，仍找不到才记删除。用 himalaya 背后的 Rust 邮件库（pimalaya）。Gmail 用应用专用密码，或用户自己注册的 OAuth 应用；不借用 Thunderbird 等其他软件的 OAuth 应用编号。以 Candid 名义的一键登录需要通过 Google 和微软的审核，按需求再评估 |
| — | MailKit 实时扩展 | Mac | 新邮件到达时由「邮件」App 调用，可拿到正文；只覆盖新邮件。新版 macOS 有扩展开关不出现的报告，实测可用后作为第 1 条的补充 |

MIME 解析用成熟的 Rust 库，不自己实现；上面列出的编码和字符集用合成邮件逐一验证。

**验证**：

- 合成邮件覆盖上面每一种编码、多段结构、只下载了一部分的邮件、没有 Message-ID 的邮件、同一封邮件在多个邮箱、删除和移动。
- 真实邮箱只在 Candid 测试版里只读试运行，只报计数：邮件数、线程数、解码失败数、不完整正文数。不给终端或开发工具开完全磁盘访问去读真实邮件。

<a id="source-filter"></a>

#### 2.0.2 来源筛选：先定级，再决定处理多深

> 设计决定：接入邮件后不能每封都处理，要有人工可设置的筛选规则，也可以加规则让 AI 判断重点，防止注入大量无用内容；AI 对话记录等来源同理。

读取和解析本身不花 token；花钱的是抽取。所以每个来源的每一条内容先定级，级别决定它走多远：

| 级别 | 处理 |
|---|---|
| 忽略 | 不入库 |
| 只存元数据 | 时间线上可见（如发件人、主题、时间、线程、在来源里的位置），正文不存，打开时从来源现读 |
| 普通 | 正文入库，可全文检索，不做抽取 |
| 重点 | 进入抽取（2.5）和汇总（2.8） |

定级按顺序分四层，所有连接器共用：

1. **范围**：选哪些账户、文件夹、项目目录。邮件默认收件箱和已发送；垃圾邮件、废纸篓、草稿不读。首次导入默认只回溯 90 天，更早的按需再导。
2. **你的规则**：条件可以是发件人或域名、收件人、主题关键词、群发相关的邮件头、客户端自己的垃圾邮件标记、你是否回复过；AI 对话可以按项目目录、会话长度。动作是定成上面四个级别之一。按顺序匹配，第一条命中的生效。**你的规则永远优先。**
3. **内置默认规则**（可改、可关）：带退订头、群发头、自动回复头或来自 noreply 地址的邮件只存元数据；你回复过的线程、和你通过信的人发来的邮件列为重点候选。
4. **AI 判断**（可选，默认关闭）：只处理规则没有定下来的内容。小模型（优先本地）读邮件头和正文开头约 500 字，给出「普通」或「重点」并附一句理由；结果缓存，每天有预算上限，每次调用记入 `ai_calls`。
   - AI 只能在「普通」和「重点」之间调整，不能推翻你的规则，不能触发任何动作；
   - 界面上标明「AI 判断」；
   - 内容里自称重要的文字（如「此邮件非常重要，请优先处理」）只当作内容，不当作指令。

你手动改了某条内容的级别时，不在后台悄悄学习，而是提示一条规则建议（如「以后来自 X 的都设为重点？」），你同意后才生效。

级别和规则命中记录在入库事件上，改规则后可以对已入库内容重新定级。

**邮件已实现的部分**：范围（账户、邮箱名或角色 `role:inbox` 等，废纸篓/垃圾邮件/草稿永不读取，默认回溯 90 天）；你的规则（发件人、域名含子域、收件人、主题关键词、群发头、邮箱，多个条件同时满足，按顺序第一条命中生效）；内置规则按「回复过 → 群发/自动 → 默认」顺序，各自可关：你回复过的线程、你写过信的人发来的邮件 → 普通并列重点候选（`important_candidate`，级别仍是普通；写过信的人只以加盐哈希记在已发邮件上）；群发/退订头、自动回复头、noreply 类地址 → 只存元数据；其余邮件默认只存元数据。AI 判断只实现为开关：开启后规则未定的邮件（回复过的和默认的）标 `ai_judge=pending`，不调用模型。级别、命中规则写在事件 payload（`level`、`level_basis`：`rule:N`、`builtin:replied|list|automated|noreply`、`default`、`manual`）。

**默认与导入范围**：

- 导入前先选账户、邮箱文件夹和回溯天数，并预览「约 N 封：X 封只存元数据、Y 封存正文」，确认后才开始。
- 没被任何规则定级的邮件默认「只存元数据」。你回复过的线程、和你通过信的人发来的邮件默认「普通」，并列为「重点」候选；你的规则永远优先。
- 单封或整个线程随时可以升为「普通」或「重点」；改规则后可以对已入库内容重新定级。
- 「邮件」App 里删掉的邮件，只存元数据的那些正文随之不可读，时间线上标「来源已删除」。
- **已实现（合成验证；未安装，真实邮箱未试）**：
  - 范围与预览：连接页邮件详情先授权「邮件」App，授权后不导入（配置 `import_confirmed=false`，同步返回 `awaiting_confirmation`）；`mail_scope` 列出账户与文件夹（只有计数）；选账户、文件夹（默认收件箱 + 已发送）和回溯（30 天 / 90 天 / 1 年 / 全部，默认 90 天）后，`dry_run` 带 `config` 预览该范围（不保存），只解析邮件头，返回各级别计数（只存元数据 / 普通 / 重点候选，被规则忽略的另计）；点「导入」才写 `import_confirmed=true` 并开始。
  - 现读：`mail_body` 按 Message-ID 从「邮件」App 的索引和 emlx 现读正文，不存、不进全文检索；邮件已删除或只剩在废纸篓/垃圾邮件/草稿时返回 `source_deleted`，界面标「来源已删除」；仅本机邮件 App 来源支持，IMAP 来源不现读。`set_level` 把单封或整个线程升为普通/重点（正文此时从来源读入并入库，可检索）或降回只存元数据（正文与检索项随之删除），记为 `manual`，规则和重新定级都不覆盖；来源已删除时不能升级。
  - 规则编辑器：有序规则，拖动或「移动」菜单调序，行内改级别，展开后改条件（可多条件）、删除；两条内置规则可开关，最后一行「其余所有邮件」固定。规则存在所有邮件来源共用的配置里。
  - 重新定级：`relevel` 按当前规则重读每封邮件（发件人、收件人不入库，所以要现读，只在内存里用）再定级；`manual` 的不动；来源里已没有的留给常规同步清理；规则设为「忽略」的已入库邮件保留为只存元数据，不删除（`ignored_kept`）；升级补正文、降级删正文；可重复运行，第二次不变。改规则后界面提示是否重新定级。
  - 界面缺口：时间线里还没有邮件轨道，打开邮件和升级目前在连接页邮件详情的「最近邮件」列表里；手动改级别后的规则建议、真实邮箱试运行、IMAP 现读未做。
- Exchange Online 的 EWS 自 2026 年 10 月起逐步关闭，以后要直连 Exchange 时按 Microsoft Graph 评估。

<a id="redaction"></a>

### 2.1 入口打码

- **一律替换**：API 密钥和访问令牌（已知前缀，或长度不少于 32、熵高的连续串）、私钥块、通过 Luhn 校验的卡号。入库前替换为 `‹redacted:类型›`，`event_text` 记一个打码标记。截图原图不改，仍受 `media` 范围约束。
- **保留但对外遮蔽**：电话、邮箱、身份证号等个人信息照常入库供你自己检索；外部访问方的结果默认遮蔽，除非它的范围明确允许。
- 打码规则对所有应用一致；误打码可以按规则关闭，不按应用写例外。

<a id="near-dup"></a>

### 2.2 近似去重

精确去重解决不了的情况：OCR 抖动、只有时间或计数变化、改了一两个字的段落。

1. **原文规范化**：统一 Unicode 宽度并去行尾空白，保留数字、大小写、内部空格与缩进。
2. **指纹成族**：同一来源与窗口，前后 10 分钟内，字符三元组的 64 位 SimHash 距离不超过 3，且编辑距离不超过 10%、数字串相同的短段落，可以记录为近似族；原段落与字符区间都保留。
3. **判新**：同窗口 30 分钟内的相同段落可减少重复模型输入；短回复带上一行作为上下文。近似族里的实际改字仍算新内容，否定、数字和代码变更不能被抹掉。
4. **边界**：近似比对限最近候选与短段落，长段落只做精确重复判断。每个原始发生记录和精确搜索都保留。

以上为 的工程选择，采用更保守的变更保留规则；早期数字骨架方案不用于生产去重。参数和资源边界以核心实现为准，固定评估与真实质量放行分开。

截图的「画面相同」判定沿用桌面采集已有的规则，这里只处理文字。阈值以评估集（2.9）实测为准。

<a id="boilerplate"></a>

### 2.3 降噪：界面固定文字

菜单、侧栏、导航、按钮这类文字在同一个应用里几乎每次都出现，会挤占摘要和检索。

- 按「应用 + 窗口类型」统计最近 7 天每个段落族的出现比例（文档频率）。出现在 30% 以上事件、且至少出现过 20 次的族，记为界面固定文字，权重随比例降低。
- 少于 4 个字的孤立短段落同样降权。
- 只降权，不删除，也不影响精确搜索命中；你可以把某个族标成「重要」取消降权（记为纠正）。
- 规则对所有应用一致，不维护按应用的黑名单。

<a id="segments"></a>

### 2.4 分段

- **活动段**：规则投影，见桌面采集 v1 §6.1。
- **片段**：相邻活动段在间隔不超过 5 分钟、且共享实体或段落族时合并；会议、通话、录音会话各自成段。片段的边界由规则决定，标题用小模型生成。
- 片段在「结束」后才进入抽取：超过 10 分钟没有新内容，或者会议、录音明确结束。

当前 先按来源、应用和窗口在 5 分钟间隔内构造屏幕片段，结束后调用一次模型；跨窗口按实体合并、结构化抽取和实体归一继续 。现有标题与摘要可手动修改，重建保留人工值。

<a id="extraction"></a>

### 2.5 抽取

- **单位**：每个结束的片段调用一次小模型。不逐张截图调用。
- **输入**：片段里新出现、未降权、注意力高的段落，按权重截取到输入上限（提议 3000 token），再附上片段的应用、时间和参与者。
- **输出**：固定的 JSON 结构，包括提到的实体、明确的承诺和请求、决定、未决问题、话题，每项都带回到原文的选择器。
- **规则**：
  - 只抽明确表述的内容；
  - 「后来没再出现」不能当作已完成；
  - 没有校准方法时，置信度留空。
- **缓存**：以输入 hash、提示词版本和模型为键，命中就不重算。换模型或提示词时生成新修订，旧结果和你的纠正都保留。
- **存放**：结果写进派生层，作为候选（`status = candidate`）。承诺类进入任务清单（第 4 节），实体类进入实体层（2.6）。

<a id="entities"></a>

### 2.6 实体层

人、项目、组织、地点、网站、应用都作为实体，和事件、片段分开存。结构如下（已在时间线库 v5 落地，`kind` 另有 `topic`、`alias_kind` 另有 `voice`，见[时间线库 §4.8.1](timeline-v1.md#derived-next)）：

```sql
CREATE TABLE entities (
  entity_id  TEXT PRIMARY KEY,
  kind       TEXT NOT NULL CHECK (kind IN ('person','project','org','place','site','app')),
  name       TEXT NOT NULL,
  status     TEXT NOT NULL CHECK (status IN ('candidate','confirmed','merged','rejected')),
  merged_into TEXT REFERENCES entities(entity_id),
  created_ms INTEGER NOT NULL, updated_ms INTEGER NOT NULL
) STRICT;
CREATE TABLE entity_aliases (       -- 名字、邮箱、账号、域名、bundle id
  entity_id  TEXT NOT NULL REFERENCES entities(entity_id) ON DELETE CASCADE,
  alias      TEXT NOT NULL,
  alias_kind TEXT NOT NULL CHECK (alias_kind IN ('name','email','handle','domain','bundle','other')),
  source     TEXT NOT NULL CHECK (source IN ('rule','model','user')),
  PRIMARY KEY (entity_id, alias, alias_kind)
) STRICT;
CREATE TABLE entity_mentions (
  entity_id  TEXT NOT NULL REFERENCES entities(entity_id) ON DELETE CASCADE,
  ref_type   TEXT NOT NULL CHECK (ref_type IN ('event','episode')),
  ref_id     TEXT NOT NULL, ref_rev INTEGER,
  selector_json TEXT,
  producer   TEXT NOT NULL, confidence REAL,
  PRIMARY KEY (entity_id, ref_type, ref_id)
) STRICT;
```

- **归一顺序**：
  1. 精确别名（邮箱、账号、域名、bundle id）；
  2. 规范化后的名字加上下文规则（同一线程、同一会议）；
  3. 仍然模糊时才问小模型，结果标为候选。
- **你的纠正优先**：合并、拆分、改名、拒绝都写进 `corrections`；重新生成派生内容后继续生效。
- 声纹识别出的说话人和这里的人物实体是两件事：自动匹配只是候选关联；你在录音里指定「这是谁」后才是确认的关联，记为别名 `alias_kind = voice`（对应语音服务的声纹人员编号）并写入 `corrections`。

<a id="speaker-labeling"></a>

**说话人标注**：

1. 录音详情的说话人列表里，每个说话人是四种状态之一：已认出（自动匹配，标「自动」，可改）、可能是某人（等你点一下）、你指定的、匿名（默认，不需要处理）。
   - 每个说话人显示**匹配度**：和此人样本中最像一段的相似度（语音服务的余弦相似度换算成百分比），并显示和第二名的差距。
   - 判定沿用语音服务的阈值：不低于匹配阈值且领先第二名足够多为「自动」；略低于阈值或领先不足为「可能是」；其余匿名。阈值以 `software/asr` 的配置为准，界面不另设。
   - 匹配度和判定一起存进说话人标注，换模型或改阈值后可以重算；你指定的不受重算影响。
2. 点一个说话人选「这是谁」：已有的人、新建一个人，或保持匿名。
3. 你的每次指定都成为这个人的样本：取这个说话人最清楚的 3 段，每人最多 20 份，超过只留最近的；只有确认过的才进样本。第一次录音时请你认一次自己。
4. 声纹库只剩一张人员列表（名字、样本数、最近出现，以及和谁容易混）：可以改名、合并、删除人，逐条删除样本或按条件清理（只留最近 N 条、删掉某次录音来的样本）。
5. 声纹向量和样本音频仍在语音服务；改名、合并、删除从核心发起并同步。删除一个人时连同样本删除，已有转写里的说话人回到匿名。
6. **整条录音整理**：物理分段和模型分块只在内部使用，一次录音先统一匿名说话人，再匹配已有声纹库；没有已登记人物也可用。短句证据不足时保留未定归属，不按文件标签新增人物；可选合并强度/人数上限属于高级设置。原文、位置、原始识别及人工命名保留，来源撤回/删除和配置变化对投影与声纹引用同样生效。实现、参数与验证统一见 [Mac 整条录音](../../apps/macos/README.md#recording-speakers)。
7. **自动匹配**：新录音默认自动转写并分说话人；每段对话里每个说话人的向量留在语音服务、转写只带引用。你确认一个人并存下样本，或在人员列表里改名、合并、删除后，所有录音按当前声纹库重新匹配，不用重新转写；结果单独保存，不改转写本身。删除录音时一并清理它的向量。

<a id="recall"></a>

### 2.7 召回

1. **解析过滤条件**：时间、应用、来源、人、项目。
2. **生成候选**：段落和元数据全文检索；两个字的中文短词按时间线库 §4.7 的两个方案之一；沿实体扩展，查到某人时连带他的别名；以后再加向量检索。
3. **排序**：在 BM25 分数上叠加新近度、注意力，再乘以「1 − 界面固定文字权重」。
4. **折叠**：同一段落族的命中合成一条，标「出现 N 次」和首次、末次时间；同一片段最多返回 3 条，保证结果多样。
5. **带证据返回**：每条都能回到原事件和文字区间。

<a id="digests"></a>

### 2.8 汇总

给 agent 和界面用的精简摘要，按小时、天、周三级生成：

| 级别 | 内容 | 上限（提议） |
|---|---|---|
| 小时 | 活动段统计、片段标题、新出现的实体 | 300 token |
| 天 | 片段列表、时间分布、未完成的承诺、主要实体 | 1500 token |
| 周 | 每天的要点、持续出现的项目和人、承诺变化 | 3000 token |

- 统计部分由规则生成，只有文字概括用小模型。
- 按输入 hash 缓存；底层数据变化（新事件、你的纠正）后，只重算受影响的级别。
- 通过新查询工具 `digest` 和 MCP 资源对外提供，范围过滤和其他工具一致。
- **日回顾**是天级汇总之上的技能（第 4.1 节）：统计和片段由规则与固定流程准备，成文由挂接的 agent 按「日回顾」技能完成，结果存为天级汇总的草稿修订；开启后按时触发并推送。现有「录音日回顾」流程并入这里。

<a id="tasks"></a>

## 4. 固定流程的最小框架

只提供固定步骤，不提供模型自行选工具的循环。功能按需开关：转写、多人分段、已有声纹匹配、标题与摘要、截图文字、抽取（承诺、请求、决定、问题、话题）、汇总统计。现有「决定与待办草稿」「标签草稿」并入抽取，「录音日回顾」并入天级汇总；日回顾成文与其他技能见 4.1。排序、归组、去重和统计优先使用规则。新增模型不自动下载，不改变已授权目的地。

统一流程目录放在 `core/workflows/`：每个流程保存版本化定义、提示模板和输出类型引用，随发布装载；运行逻辑留在现有 store/service 模块。用户开关、角色映射与预算作为独立配置保存，不修改发布定义。外部 AI 的 `agents/skills/` 单独维护，不作为内部可执行脚本目录。目录已随固定处理实现，当前定义、提示和输出校验在该目录维护。

闭环：选取已保存输入 → 按版本固定步骤 → 规则或角色模型 → 校验结构与来源 → 保存新修订 → 更新索引和处理状态。

| 共享对象（逻辑设计，非已新增字段） | 内容与所有者 |
|---|---|
| 来源记录 | 稳定发生身份、来源版本、时间/样本区间、原件引用与授权；store 管理 |
| 录音与分段 | 一次开始至结束一个 recording 身份；segment 有序号、源样本区间、保存确认与缺口；分段复用既有原件 |
| 流程定义 | ID/版本、输入类型、固定步骤、触发、输出校验器、角色、预算；随版本发布，不执行任意脚本 |
| 运行与步骤 | 输入修订快照、配置版本、步骤检查点、尝试次数、租约与取消标记；唯一调度者 Rust |
| 模型角色 | asr、speaker、title、summary、ocr 等映射至 provider/model/runtime/目的地；设置页编辑同一配置 |
| 派生与纠正 | artifact 身份/修订、来源选择区间、规则或模型/提示版本、置信度；人工纠正独立保存并优先展示 |

首次贯通选择「连续录音→转写→标题→可选摘要」。保存分段后即可增量转写，整段结束时收束；重叠窗按源样本位置对齐，真实重复说话保留。多人分段和已有声纹匹配按开关追加，未知身份保持匿名。先用时间生成可用标题，模型标题为草稿；人工改过的标题不被重跑覆盖。摘要关闭或失败不阻断原音、转写与播放。

流程定义只需列出：输入 recording 的版本，transcribe 步骤调用 asr 角色，title 步骤读取转写，summary 步骤带独立开关。每步声明输出类型、最大输入/输出、超时和依赖。增加「标签」只加一个定义、输出校验器、提示模板与合成验收样例；现有模型适配足够时不新增调度器、存储或 UI 状态机。

### 调度、成本与恢复

- 手动、封存事件、定时三种触发汇入一个队列；未启用的流程不排队。启动时恢复持久任务，不重扫全库造新任务。
- 状态：排队、运行、等待条件、成功、失败、已取消、已跳过。等待条件细分缺模型、未授权、预算不足；不静默改用远端。步骤有开始/结束和错误，界面可解释卡在哪。
- 幂等键包含来源发生身份、输入修订、流程版本、有效配置；同内容两次录音不合并。步骤结果和检查点事务提交，事件投递允许重试，索引更新按修订去重。
- 领取用租约和尝试号；崩溃后重领过期任务。结果提交核对尝试号、取消、源修订和权限，迟到结果不能覆盖新结果。已完成步骤复用，失败只重试可重试步骤。
- 单次/每日 token、费用、时长与并发限制由服务执行；调用前预留预算，调用后结算。用量未知记未知，不能记零；网络失败时不能假定未计费，先核对提供方请求状态。
- 取消先持久化，再取消外部模型请求并阻止后续步骤；提供方无法取消时记录仍可能计费，迟到输出不发布。资源并发有统一上限，采集保存优先。
- 调用记录进入 ai_calls，并关联运行/步骤、模型版本、目的地、用量与错误；不把原文复制到日志。设置迁移保留原授权，密钥只通过平台密钥接口读取。

### 来源、权限与修订

沿用 artifact 公共封套；样本/字符使用半开区间。事件记录发生，派生记录解释，人工纠正记录用户选择；不覆盖原文。模型输出必须有可定位来源，引用越界、缺源或类型错误拒绝发布。

有效权限取输入来源交集，在选择输入、发往模型、提交和对外查询时检查。来源修订使旧派生退出默认索引、安排新修订；删除或撤权取消相关排队任务、拒收迟到结果并使派生/索引/缓存失效。历史保留服从删除策略，回退不能恢复已撤权或删除的正文。外部 AI 默认只读，内部授权草稿写入不授予外部写权限。

表结构与外部模型服务协议实施时由架构实施包的核心负责人统一提交版本、旧库读取、未知版本拒绝、失败恢复与消费者验证；媒体、队列和记录修订的 v3 升级已实现；固定处理定义、配置与输出采用各自版本化格式，仍需按变更范围验证兼容与消费者。

### 4.1 两种方式：核心内自动与挂接的 agent

> 设计决定：AI 页保留，能在 App 里和 AI 对话、操作内容。agent 不自己做，挂接外部的 Pi，用我们自己的界面、插件和严格护栏（只能读写特定范围），这样不用自己做 agent harness，也能提供面向用户的能力；不用 pi-agent-core 自建循环。功能分两种：核心内自动触发的简单功能；基于钩子、技能和自定义约束调用的外部 agent。另外提供 MCP/API 给外部 agent 接入，一般用户不会用。此决定替代同日早些时候「内部只做固定流程、内置 pi 撤销」的说法（智能处理）。

| 方式 | 是什么 | 例子 |
|---|---|---|
| **核心内自动** | 规则或固定步骤（可调一次角色模型），由事件自动触发；调度、预算与恢复按本节上文 | 去重降噪、转写、录音命名、OCR、片段标题、抽取、邮件定级 |
| **挂接的 agent** | Pi 在 AI 页和你对话，或由钩子启动；用我们的技能、插件工具和护栏 | 对话与操作内容、日回顾、资料与回复检索、提醒提案 |
| 附：对外接口 | MCP 与 API，让 Claude Code、Codex 等接入；同一套工具和权限 | 给高级用户 |

**Pi 的接入方式**：

- 版本：`@earendil-works/pi-coding-agent` 1.5.2（npm 锁定在 `agents/pi-extension/package-lock.json`），随 App 打包 Node 24.22.2（官方包，按固定 SHA-256 校验）。升级 Pi 须重新核实下列参数与隔离。
- 以 RPC 模式（`--mode rpc`，标准输入输出上的 JSON 行协议，只按 LF 分行）作为 App 管理的后台进程运行；聊天界面完全由 AI 页自己画。
- 实测的启动参数：`--no-builtin-tools --no-extensions -e <我们的插件> --tools 'pv_*' --no-mcp --no-skills --no-prompt-templates --no-themes --no-context-files --no-approve --offline --system-prompt <我们的提示> --provider candid --model agent_chat --session-dir <独立目录>`。注意这一版是 `--no-extensions`（复数），它同时关掉内置插件（MCP、codemode）；显式 `-e` 仍加载。
- 隔离：环境变量只给 `HOME` 与 `PI_CODING_AGENT_DIR`（都指向 App 数据目录下的 `pi/`）、`PI_OFFLINE`、`PI_SKIP_VERSION_CHECK`、`PI_TELEMETRY=0` 和本次运行的核心地址与令牌，不继承用户的环境（密钥、代理、PATH）。对照实验：伪造的 `~/.pi/agent` 里放插件与设置，不加隔离时会被加载，加隔离后不加载。工作目录是空目录，项目信任一律拒绝。
- 模型：插件注册唯一的提供方 `candid`（OpenAI 兼容），指向插件在本机回环上开的随机端口与随机路径；每次请求转给核心 `POST /local/pi/model`，由核心用冻结的 `agent_chat` 模型和钥匙串里的密钥发出，记入 `ai_calls`（`client = pi`）。Pi 和模型都拿不到服务商密钥。核心对上游不流式，插件把整段回答按 SSE 一次回放给 Pi（文字不逐字出现，待改进）。目前只接 OpenAI 兼容与 Ollama 接口；云端模型须本次运行允许远程。
- 每次运行由 App 调 `POST /local/pi/start` 冻结模型、范围（来源、写入档、提案种类、AI 会话来源）与预算（模型调用次数、工具调用次数、输出 token），核心为专用访问方 `candid-pi` 换发令牌；`POST /local/pi/stop` 后令牌失效。超预算即停止本次运行，崩溃重启不重置预算。

**护栏：工具三档，权限在核心里检查**。插件提供的每个工具都调用核心（本机套接字，带本次运行的令牌），核心按 `candid-pi` 的范围检查并写访问日志；Pi 手上没有别的工具。插件里隐藏工具只是方便，权限只看核心。

| 档 | 能做什么 | Pi 的工具 → 核心工具 |
|---|---|---|
| 读 | 查时间线、片段、汇总、资料；现读邮件正文与 AI 会话 | `pv_status`、`pv_overview`、`pv_search`、`pv_timeline`、`pv_context`、`pv_get_event`（含已入库的邮件正文；从邮箱现读正文还没有核心工具）、`pv_episodes`、`pv_episode`、`pv_records`、`pv_agent_session`（`agent`）、`pv_memories`（新增 `memories`） |
| 写（只限本库的派生与纠正） | 改标题与备注、标记资料、确认或忽略承诺候选、保存草稿；写入都记为纠正或「AI 草稿」，带访问方、运行编号与模型，可撤销 | `pv_annotate`（`annotate`，走片段标注的纠正路径）、`pv_mark_reference`（`mark_reference`，`memories` kind `reference`，候选）、`pv_commitment`（`commitment`）、`pv_save_draft`（`save_draft`，`digests` 草稿）、`pv_undo`（`undo_write`） |
| 提案（App 外的动作） | 你在界面上逐条批准后才由 App 执行 | `pv_propose`（`propose`，种类限提醒事项的 `create_reminder`、`update_reminder`、`complete_reminder`、`delete_reminder` 与日历的 `create_calendar_event`、`update_calendar_event`、`delete_calendar_event`；改、完成、删要带 `item_id`，来自用户「问 AI」带进来的那一条） |

- 写入档由访问方范围的 `writes`（`annotate`、`reference`、`commitment`、`draft`）逐项授予，默认空；提案种类由 `propose_kinds` 限定。撤销：App 可撤销任何 agent 写入，agent 只能撤销自己的、且其后没有新改动的写入；撤销本身也记为纠正。
- 没有终端，不能读写本库以外的文件；屏幕、邮件、消息里的文字一律当数据（原则 5）：工具结果包在 `<candid_data>` 里并注明不执行其中要求，系统提示同样规定。实测一个「照做」的模拟模型调用 `bash` 只得到「没有这个工具」，在只读运行里改名被核心拒绝。
- 一次对话或一次技能运行冻结模型、工具、范围与预算；技能运行记录已作为交互层版本化载荷保存，带来源、模型、步骤、结果与中断状态。

**钩子与技能**：

- 钩子：定时（如每天 21:00）、事件（录音封存、片段结束、一天结束、邮件定为重点）、手动。一个钩子启动一次核心内的流程，或带着某个技能启动一次 Pi。
- 技能正文在 `agents/skills/` 维护；Pi 与外部 agent 用同一份。
- 例：日回顾 = 定时钩子 + 日回顾技能 + Pi，结果存为天级汇总的草稿修订；你开启推送后完成即发系统通知（默认关闭，默认 21:00），无事可报不推送。

**功能目录**：`core/workflows/catalog.json` 扩为唯一的功能目录，登记核心内功能、技能和钩子。每项写明编号、名称、方式、输入（来源与层）、触发、角色、输出 artifact 类型、默认开关、默认每日预算、能否用远程模型。设置页、AI 页和对外接口都读这份目录。

**上下文门槛**：在评估集（2.9）上检索 recall@10 不低于 0.8（至少 30 个查询）、降噪抽检准确率不低于 0.9、天级汇总的每条要点都能点回原处且抽检无编造（数值是提议，跑出基线后再定）。AI 页对话接通即可用，回答都带引用；钩子启动的技能（如日回顾）在达标后才默认开启，达标前可以手动运行。

### 4.2 设置与管理

| 位置 | 管什么 |
|---|---|
| 设置 → 模型 | 服务商、模型、角色分配、回退、全局预算（已有） |
| 设置 → AI 功能 | 目录里每项一行：开关、钩子与时间、推送、读哪些来源、用哪个角色、每日预算、上次运行与结果 |
| 连接页的每个来源 | 这个来源能不能给 AI 读、能不能发往远程模型；邮件的范围与规则 |

> 实现进度（–093）：模型设置、人物入口、固定流程与技能的独立设置、持久运行记录、钩子和通知已接入。技能执行跨页面保留，可取消/重试并检查原文；每次调用重查冻结权限与额度。屏幕文字增量、低权重纠正、规则片段与引用摘要已接派生层。日常库未加载合格质量报告，自动技能仍等待评估；通知默认关闭。模型统计卡片、小图和额外能力推理测试未加入。

- 一个功能能读哪些来源，取功能设置与来源授权的交集；能不能用远程模型，取功能设置、来源授权、角色目的地三者中最严的。本机（回环地址）上的模型服务不论标为本机还是自托管，都不需要逐来源批准（设计决定：隐私靠用户自愿，不做过多处理）。
- 对话运行可刷新权限与模型范围，但必须带回当前对话的有界历史及本地时间；简短追问延续主题。邮件任务直接按 `mail.message` 列表并展开原文，不以屏幕里的邮件关键词或应用时长替代。普通回答不主动展开采集缺口，屏幕缺口不推导为邮件缺失。首页省略空的可选翻页参数，真实游标仍须同工具、同筛选条件使用。
- App 在冻结运行时附带邮件能力状态：未连接、未授权或不在本次范围时直接说明恢复入口；不把无权读取推断成没有邮件，不暴露关闭来源的标识、地址或正文。
- 设计决定：日程和提醒交给 Agent 管理，移除手动新建与编辑表单；保留展示、问 AI 和提案批准。
- **AI 页是在 App 里使用 AI 的地方**，不放开关。一页两栏：
  - 左栏「今天」，自上而下：日程（系统日历，只读）、提醒（系统「提醒事项」今天和逾期的，加上 AI 提的候选，候选用虚线框，可「加到提醒」或忽略）、待你处理（待批准的提案、要你确认的说话人和资料候选）、回顾（最近一次日回顾）；底部一行显示正在处理的任务，点开可取消、重试、看失败原因；
  - 右栏对话：和 Pi 对话，让它查找、整理、改标题、标资料；左栏任何一条可「问 AI」，作为上下文带进对话；它要做的写入和提案在对话里逐条显示，本库内的写入直接做、可撤销，App 外的提案要你点批准；对话只存在本机，「历史对话」按今天/昨天/更早分组、可搜索，每条显示标题（默认取第一个问题，可改名）、时间、最后回答预览和引用记录数，可删除，打开后恢复卡片；
  - 窗口窄于 900pt 时两栏变成顶部切换「今天 / 对话」；
  - 时间线首页看过去，AI 页看今天和接下来，日程不进时间线。
- **日程读取与编辑**：通过 EventKit 读系统日历和提醒事项，不入库，每次打开 AI 页时取今天和逾期的；默认读全部日历，可在连接页排除。你在左栏可以直接新建、修改（标题、时间、备注）、完成或删除提醒，新建、修改或删除日程，这是你自己的操作，不走提案；删除在原地再确认一次。Pi 要做同样的改动只能提案（4.3），删除的提案批准时同样再确认一次（设计决定，）。
- **技能与耗时操作**：AI 页头部「技能」列出挂接 Pi 能运行的技能（名称、一句说明、触发方式、是否开启、运行）和核心内流程；各功能的设置之后放在 设置 → AI 功能。「回顾今天」= 运行日回顾技能（Pi 读全部允许的来源，`pv_save_draft` 存天级草稿），不再只看录音。回顾、会前要点、运行技能等可能要等的操作，点后变成进度加「取消」，取消即中止这一轮；页面上能点的都做成按钮、胶囊或图标按钮（设计决定，）。
- **对话的呈现**：Pi 的回答上方一行写它查了什么（「查了 3 条记录 · 录音 11月12日 15:30、邮件 2 条」，可展开看每次调用和参数），调用进行中显示「正在搜索「预算」…」；正文按 Markdown 排版；Pi 按系统提示把引用写成 `[[event_id]]`，界面显示成可点的「录音 11月10日 10:14」并跳到时间线上那一刻，漏写的裸 id 同样转换；输入 @ 可引用一条记录作为上下文。
- 声纹库从 AI 页移到「人物」：先作为设置里的一页，人物页做好后迁过去。
- 每条 AI 产出都能看到谁生成的（规则、模型或 Pi）、依据哪些记录（可点回原处）、什么时候；都能改、确认或拒绝，改动写进 `corrections`，重算后仍生效。
- 派生结果的旧修订：保留最新的、你确认或改过的、被提案引用的；其余旧草稿 30 天后清理。

<a id="commitments"></a>

### 4.3 承诺与提醒

1. 片段结束后的抽取（2.5）产出承诺、请求、截止时间等候选，存为 `memories`（`kind = commitment`，候选状态）。
2. 候选出现在日回顾和 AI 页「待你处理」，可以确认、修改或忽略。
3. 确认后生成提案（`create_reminder` 或 `create_calendar_event`）；你逐条批准后，App 通过系统接口写入「提醒事项」或日历，回执写回提案。暂不做自动批准。实现：App 专用的 `POST /local/agenda`（带令牌一律拒绝）列出待处理项并推进提案 `pending → approved → executed | failed`（失败可重试或拒绝），批准先记入核心再写系统，回执（`receipt.item_id`）或失败原因写回提案；AI 页「加到提醒」= 确认候选 + 生成提案 + 批准。
4. 你的处理回传给下一次抽取；「后来没再出现」不当作已完成。

### 4.4 资料与回复检索

- 在邮件、文件、片段、你发出的消息上可以「收藏为资料」，可选加标签（如「请假回复」「报销流程」）；存为 `memories`（`kind = reference`，你创建即已确认），只存引用和标签，原文留在原处。
- 你发出的邮件、多次修改过的文字自动列为资料候选，你确认后才算。
- 技能「查资料与回复模板」按问题检索资料与相关片段，返回带出处的原文和一份回复草稿；草稿只供复制或修改，不代发。挂接的 Pi 与外部 AI 用同一个技能。

## 5. 执行位置

Rust store 保存作业与结果，service 调度并路由模型；语音与其他模型通过外部服务接口调用；本体不启动 Python worker 或管理其环境。Swift 负责系统能力、设置和状态展示。Hub 旧队列的过渡和代码路径见架构。挂接的 agent（4.1）：Pi 以 RPC 模式作为 App 管理的进程运行，界面由 AI 页自己画，工具只有我们插件提供的读、本库写和提案三档；Codex、Claude Code 等外部 AI 经 MCP/API 使用同一套技能和工具，pi 会话读取保留。核心里不做 Agent 后端或工具循环。

## 6. 研究议题

这一节只列问题和对比方法，不给默认实现。

### 6.1 记忆与人格

先回答用途，再定结构：

- **画像拿来做什么**：调整回答方式、判断什么值得提醒、给建议，还是给外部 agent 当背景？用途不同，所需的结构和证据门槛完全不同。
- **分几层**：事实、偏好、行为模式、特质。每层各有多高的证据门槛，有效期多长，谁可以写入。
- **变化**：过去的观点、现在的观点和模型推测分开保存（已在智能处理规范中）；冲突时怎么提示你。
- **注入方式**：常驻的核心画像要小、有上限；其余按需检索。
- **整理与审阅**：定期把候选提炼成长期记忆，并给你一份可审阅的变更说明；同一结论至少在两个独立场合出现才沉淀。
- **遗忘**：删除一条记忆或一个来源时，连带删除由它派生的内容；借助派生关系做到，并提供预演。
- **权限**：画像和人格推断默认关闭，开启要你单独确认；优先用本地模型；对外部访问方单独一个范围，默认不开放。

对比方法：在你的数据上用本地模型离线运行两三种候选做法，比如「带证据的结构化记录」「可编辑的 markdown 画像」「两者结合」，由你判断哪种更准、更有用，再写规格。

### 6.2 「你关心什么」

信号来源：

- 话题和实体出现的频率与持续时间；
- 你主动做过的动作：标记、搜索、回访、停留；
- 承诺和决定涉及的对象。

待研究：几种信号怎么加权，怎么随时间衰减，怎么区分「被动看到」和「主动关注」。

### 6.3 主动打扰

什么情况值得发通知，频率上限多少，和专注状态怎么配合。在这之前，任务结果只出现在 App 内；唯一的例外是你开启了推送的钩子（如日回顾，4.1），默认关闭。
