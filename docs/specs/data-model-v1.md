# 数据模型 v1：分层、证据分级与存储预算

**中文** · [English](data-model-v1.en.md)

**状态**：设计已定，待验证（第 13 节）。本文接受后，取代[时间线库 v1](timeline-v1.md) 第 2.2 节（数据根目录布局）、第 4 节（数据结构）和第 9 节（现有数据迁移）；查询接口、连接器和访问规则仍以时间线库 v1 为准，数据整理流程仍以 [Agent 基座 v1](agent-platform-v1.md) 为准。

## 1. 现状：空间花在哪里

2026-11-18 对迁移后资料库的测量，覆盖 2026-08-17 至 11-18 共 94 天，总计 6.8 GB：

| 项目 | 规模 | 问题 |
|---|---|---|
| 截图原件（JPEG） | 14,610 张，4.6 GB，平均 328 KB，约 1900×1230 | 占全部空间约七成；有采集的日子平均每天约 1,240 张 |
| 旧桌面台账的截图 | 481 MB | 切换到直写后仍保留的重复副本 |
| `store_meta` | 256 MB | 截屏片段的输入（`screen.input`）和修订（`screen.revision`）各 1,015 条，两份等大；键值配置表被当成文档仓库 |
| `episode_evidence` | 114 MB | 证据定位（`selector_json`）平均 12.6 KB，最长 113 KB，存了正文副本 |
| `source_cursors` | 112 MB | 单个 AI 会话的同步进度最长 6.5 MB |
| 派生 JSON 原件 | 19,739 个，435 MB | 识别结果整份存成文件 |
| 日志类表 | 访问日志 15.7 万行，变更 15.2 万行，AI 会话条目 14.3 万行 | 只增不减，没有保留期 |
| 录音（WAV） | 54 段，140 MB | 平均每段 2.6 MB，未压缩 |

已经起作用的：段落去重。96,852 次文字引用只存了 39,606 段正文，压缩约 2.4 倍。

另外有十张表是空的或几乎是空的：`memories`、`memory_sources`、`entity_mentions`、`digests`、`proposals`、`record_audit`、`record_revisions`、`record_selected`、`ingest_conflicts`、`entities`（2 行）。

> 结论：空间问题集中在截图编码和重复保存，数据库问题集中在「把大段内容塞进不该放的地方」。两者都靠结构和策略解决，不需要牺牲可追溯性。

## 2. 初期功能与所需数据

第一版做扎实前五项，后两项只留位置：

| 功能 | 典型问题 | 需要的数据 |
|---|---|---|
| 回忆与检索 | 「上周和某某聊过预算吗」 | 记录、段落全文索引、人物 |
| 给 agent 的上下文 | 「我在做什么、最近关心什么」 | 片段摘要、当前状态、小而精的画像 |
| 承诺与待办 | 「我答应过谁什么」 | 从片段抽取的承诺，带出处和处理状态 |
| 日回顾 | 「今天干了什么」 | 片段、时间统计 |
| 人物和项目页 | 「和某某的所有往来」 | 实体、别名、提及 |
| 画像与偏好（留位置） | 「我喜欢怎样的回复」 | 长期记忆，证据门槛高 |
| 主动建议（留位置） | 「现在该提醒什么」 | 以上各层加注意力信号 |

这些功能需要的数据高度重合：带出处的记录、片段、实体、抽取结果。schema 围绕这几样东西设计，不为单个功能建表。

<a id="principles"></a>

## 3. 原则

1. **记录可以精简，但每次精简都留痕。** 原件和记录允许按规则降级或删除，前提是：写下精简了什么、按哪条规则、何时、省了多少；引用它的派生内容和记忆仍然成立，只是出处标明「原件已压缩为文字」或「原件已删除」。
2. **去重分三个时机**：采集时不写重复的（画面没变、文字没新内容）；入库时按内容寻址合并（同一份字节、同一段文字只存一次）；事后整理时合并近似的（相邻的近似截图、近似段落族）。
3. **规则是数据，不写进 schema。** schema 提供分级、保真度、精简记录和用量统计这些「挂钩」；具体策略（多久降级、阈值多少）存成可修改的策略行，由核心的整理任务执行。
4. **你的标记和纠正优先于任何自动规则。** 被你钉住的内容、你的纠正直接指向的证据，自动整理不会动。
5. **派生内容可以删掉重算，你的纠正不会被重算覆盖。**
6. **大段内容只存一份。** 正文进段落表，二进制进原件仓库；其他地方只存引用和区间，不存副本。

<a id="layers"></a>

## 4. 分层

| 层 | 内容 | 可变性 |
|---|---|---|
| **原件** | 截图、录音、附件的字节，按内容哈希存放 | 字节不改；可以被更省空间的表示替换（见第 6 节） |
| **记录** | 来源上报的事实：窗口切换、收到邮件、你发给 AI 的话 | 内容不改；时间范围只能延长（合并重复时）；可以按规则删除 |
| **派生** | OCR、转写、片段、抽取结果、实体候选、索引 | 可以整体删除后重算；必须写明生成者、模型、提示词版本、置信度 |
| **记忆** | 整合后的人物、事实、偏好、承诺 | 有修订记录；每条都链接到下层证据 |
| **纠正** | 你的改名、合并、标记、删除决定 | 独立保存，重算后仍然生效 |

> OCR 和转写属于派生，不属于记录：它们由原件经模型生成，换了模型可以重算。现在 `store_meta` 里的截屏片段输入就放错了层。

<a id="tiers"></a>

## 5. 证据分级

每条记录和每个原件都有一个**保留级别**，决定自动整理时的先后和底线：

| 级别 | 含义 | 自动整理 |
|---|---|---|
| `pinned` 钉住 | 你手动标记的，或你的纠正直接指向的 | 不动 |
| `key` 关键 | 被片段或抽取结果当作主要证据 | 排在普通之后处理，底线由策略决定 |
| `normal` 普通 | 一般记录 | 按策略降级 |
| `ephemeral` 临时 | 没有新内容的重复帧、界面固定文字为主的截图、被合并掉的近似项 | 最先清理 |

- 级别由规则计算，你可以手动覆盖；手动覆盖记为纠正，规则重算不会改掉。
- 引用关系变化时级别随之上调；引用消失后可以回落。
- **记忆不要求对应到具体的文字或截图。** 一条关键事实往往是从许多片段、多次过程里归纳出来的，它的证据是片段和抽取结果这些派生内容，而不是某一张图。所以记忆不会把原件钉住，原件被压缩或删除也不影响记忆成立；证据链只需要能往下追到它实际依据的那一层。
- 记录本身之外，级别也作用于它的原件：同一张截图被多条记录引用时，取最高的级别。

<a id="fidelity"></a>

## 6. 保真度阶梯与精简记录

原件按类型有一条保真度阶梯，自动整理只会沿阶梯往下走：

| 类型 | 阶梯（从高到低） |
|---|---|
| 截图 | 入库即为 WebP（见第 9 节） → 缩略图 → 只留文字（OCR 结果保留） → 只留记录元数据 |
| 录音 | 处理用的 WAV（处理完即删） → AAC（见第 9 节） → 只留转写 → 只留记录元数据 |
| 附件、文档 | 原件 → 只留提取的文字 → 只留元数据 |
| 派生 JSON | 结构化入表后删除文件；必须保留的用压缩格式存放 |

每一次降级都写进 **精简记录**（`reductions`）：对象、原保真度、新保真度、规则编号、时间、前后字节数。精简不可撤销，所以执行前要能**预演**：会释放多少空间、影响哪些条目、哪些引用会变成「只剩文字」。

<a id="dedup"></a>

## 7. 去重

| 时机 | 做法 | schema 需要的支持 |
|---|---|---|
| 采集时 | 画面和上一张相同（感知哈希距离在阈值内）就不存新图，改为延长上一条记录的时间范围并计数 | 记录有 `end_ms` 和 `repeat_count`，允许只延长不改内容 |
| 入库时 | 同一份字节只存一次（内容哈希）；同一段文字只存一次（段落哈希，已实现） | `blobs` 以哈希为键；`text_chunks` 以规范化哈希唯一 |
| 入库时 | 近似段落归族（SimHash，规则见 Agent 基座 2.2） | 段落族表 `chunk_families` |
| 事后整理 | 相邻的近似截图合并为一条，只保留代表帧；被合并的降为 `ephemeral` 后按策略清理 | 原件有感知哈希 `phash`；精简记录写明合并关系 |

近似合并的底线沿用 Agent 基座 2.2：数字、否定、代码的变化算新内容，不能被合并掉。

<a id="budget"></a>

## 8. 存储预算

- **你设上限**：总量上限，可再按类别细分（截图、录音、文字与数据库），完全由你决定。界面根据实测的压缩效果给出参考：按你最近的采集量，某个上限大约能保留多少天的截图、多少小时的录音。
- **用量统计**：按「类别 × 保留级别 × 日期」维护用量汇总表，界面和整理任务直接读，不用每次扫描全库。
- **超出时**：整理任务按「级别从低到高、时间从旧到新、保真度从高到低」挑选降级对象，直到回到上限以下；钉住的不动。
- **先预演，再执行**：自动整理第一次触发或单次影响较大时，先给你一份预演说明；你可以设成以后自动执行。
- **策略存为数据**：保留天数、阈值、编码参数都是策略行，改策略不需要改 schema，也不需要迁移。

<a id="storage"></a>

## 9. 节省空间的存储方案

以下为工程选择，数值都要在你的数据上实测后定：

1. **截图存为 WebP（质量约 60）**。2026-11-18 用 12 张真实截图（约 1920×1130）实测：

   | 格式 | 平均大小 | OCR 字符召回（平均 / 最低） |
   |---|---|---|
   | 现在的 JPEG | 364 KB | 基准 |
   | JPEG 质量 40 | 185 KB | 94.5% / 77.0% |
   | **WebP 质量 60** | **122 KB** | 92.0% / 82.4% |
   | HEIC 质量 50 | 153 KB | 94.0% / 90.0% |
   | AVIF 质量 50 | 124 KB | 92.0% / 85.1% |

   - 各格式的识别率差距在 OCR 本身的波动范围内，裁出同一块文字区域肉眼看不出差别。实测是在已有 JPEG 上二次压缩，从采集的原始画面直接编码只会更好。
   - 选 WebP：约为现在的三分之一，编码快；Windows、浏览器都能直接显示，以后的网页界面和 Windows 版不需要转码。HEIC 在 Windows 上要额外装扩展，浏览器基本不支持；AVIF 大小相当但编码慢；JPEG 同样清晰度下约大一半。
   - OCR 在压缩前对原始画面做；存下来的图主要给人看，以及以后需要时再识别。
   - 副屏、非焦点窗口可以再降分辨率。
2. **截图去重**：采集时的感知哈希去重，加上事后的相邻近似合并。
3. **截图按年龄降级（默认开启）**：临时级 7 天后清理；普通级 30 天后降为缩略图，90 天后只留文字；关键级 90 天后降为缩略图。天数是策略，可在设置里改或关闭；超出存储上限时第 8 节的预算优先。
4. **录音**：Mac 录音边录边写成 AAC（分片 MP4，每秒定稿一次），不再先写 WAV 再转码；意外退出时最后一个未定稿的片段之前都能恢复。录音在磁盘上按 10 分钟一个分段存放，用户看不到分段。旧的 WAV 分段处理完后转成 AAC。实测一段 30 秒、48 kHz 单声道录音：WAV 2.9 MB，Opus 24 kbps 89 KB，AAC 32 kbps 128 KB，MP3 32 kbps 120 KB，都缩小二十倍以上。

   - **选 AAC（`.m4a`），单声道，48 kbps，采样率不低于 16 kHz**：Mac 和 Windows 都能用系统自带的编码器，到处都能播放。转写模型识别前都重采样到 16 kHz 单声道，更高的采样率用不上；48 kbps 比测试的 32 kbps 多留余量，体积约为 WAV 的十五分之一。
   - 不选 MP3：低码率下最差，32 kbps 会把频段砍到 8 kHz 左右。Opus 同样清晰度下更小，但 Mac 上要额外带编码库。
   - **放行条件**：同一段录音压缩前后，转写结果基本一致，且声纹匹配分数下降不超过阈值。声纹模型对压缩失真比转写更敏感；但目前声纹识别本身的信度偏低，要先把它的基线做可靠，这一条才有判别力。
5. **数据库瘦身**：
   - `store_meta` 只放小配置；截屏片段的输入和修订进派生层的表，不再存两份。
   - 证据定位只存段落编号和字符区间，不存正文。
   - 同步进度只存位置，不存内容。
   - 派生 JSON 入表，或用 zstd 压缩存放。
6. **日志保留期**：变更流在所有订阅方确认后压缩；访问日志超过 N 天后汇总成按天、按访问方的统计；AI 会话条目按来源的保留设置清理。
7. **旧存储退役**：只保留一个数据根目录；旧桌面台账和旧媒体库在本次转换后删除，核心里对应的迁移和对账代码一并删除。

<a id="tables"></a>

## 10. 表清单（骨架）

只列表和关键字段，完整 DDL 在评审通过后补。

**来源与记录**

- `sources`：来源和授权。
- `source_cursors`：同步位置，只存位置，有大小上限。
- `events`：记录。新增 `end_ms` 可延长、`repeat_count`、`tier`、`tier_by`（规则还是你）。
- `threads`：会议、对话、邮件串。

**原件与文字**

- `blobs`：以 `sha256` 为键。新增 `fidelity`、`codec`、`phash`、`replaced_by`（降级后指向新的表示）、`tier`。
- `event_blobs`：记录和原件的关系，指向当前表示。
- `text_chunks`、`event_text`：段落和引用（沿用）。
- `chunk_families`：近似段落族。
- 全文索引：可重建的投影（沿用）。

**派生与记忆**

- `episodes`：片段（沿用修订模型）。
- `extractions`：承诺、请求、决定、问题、话题，带处理状态。
- `entities`、`entity_aliases`、`entity_mentions`：人物和项目。
- `memories`：长期记忆，通用结构（类型、内容、修订、状态）；具体分层留待研究结论。
- `evidence`：统一的证据链接表。派生和记忆都通过它指向下层（记录、段落区间、原件区间），带角色和简短定位。取代现在各自的证据表。
- `corrections`：你的纠正。

**存储治理**

- `retention_policies`：策略行。
- `reductions`：精简记录。
- `storage_usage`：用量汇总。

**运行、访问与审计**

- `jobs`、`job_checkpoints`：处理任务（沿用），与数据分开。
- `changes`、`tombstones`：变更流和墓碑（沿用；墓碑原因增加 `compacted`）。
- `clients`、`access_log`、`proposals`：访问方、审计（加保留期）、外部动作提案。
- `ai_providers`、`ai_models`、`ai_roles`、`ai_calls`：模型和用量（沿用）。
- `settings`：小配置，取代 `store_meta` 的配置用途。

**删除**：`media_migrations` 等 Personavia 迁移用的表；`record_audit`、`record_revisions`、`record_selected`、`digests` 等未启用的表，等到真正需要时按本文的骨架重新加。

<a id="deletion"></a>

## 11. 删除与压缩的连带关系

1. 删除或压缩前先算出受影响的集合：由目标派生的内容、引用它的记忆和纠正、会失效的索引条目。预演和执行用同一套计算。
2. **删除**：写墓碑，立即对查询和 agent 隐藏；取消相关作业；删除派生内容和索引；清理无人引用的段落和原件（沿用时间线库 v1 的删除顺序）。
3. **压缩**：不写墓碑，写精简记录；原件替换为低一级的表示；引用它的证据链接标为「已压缩」，引用仍然有效。
4. 迟到的作业在提交前检查墓碑和精简记录，已删除或已压缩的内容不会被重新生成或还原。

<a id="migration"></a>

## 12. 从 v8 升级

v0.1.0 已公开发布，别人手上可能已有 v8 的库，所以不另起新库，沿用核心的事务升级链（v8 → v9 → …），每一步打开库时自动执行、失败回滚。分步进行：

| 版本 | 内容 | 状态 |
|---|---|---|
| v9 | 删除只写不读的截屏片段修订；片段输入不再存原文，用时从段落表重建 | 已实现。真实资料副本：数据库 1,038 MB → 857 MB；8,525 帧、478,589 行重建结果与原文逐字一致 |
| v10 | 片段输入和证据定位不再逐行重复事件 ID 和段落族哈希；证据定位改为 `screen-selector/2`，查询接口读取时还原成原来的格式 | 已实现。真实资料副本：v8 → v10 共 1,038 MB → 701 MB，首次打开升级 13 秒；478,589 行证据还原后与原文逐字一致 |
| 下一步 | `screen.text` 记录里内嵌的证据（约 100 MB）同样改为引用 | 待做；它属于记录本身，要先确认不影响记录指纹 |
| 下一步 | AI 会话条目：文件路径和哈希只存一次，条目引用编号；之后再把旧格式的会话进度转出 | 待做。实测直接逐行转出会让表从 82 MB 涨到 221 MB，必须先去掉重复 |
| 一次性转换 | 已有截图转 WebP、派生 JSON 压缩（raw DEFLATE）、旧 WAV 录音转 AAC、WAL 上限 | 已实现。真实资料库：截图 4.91 GB → 1.51 GB（14,610 张，约 4 分钟），派生 JSON 456 MB → 61 MB，WAL 805 MB → 15 MB |
| 旧桌面台账 | 逐字节核对无差异后移出资料库 | 已在作者本机执行，约 540 MB；对应的迁移和对账代码仍待删除 |

**已决定**（2026-11-18）：

1. 存储上限由你设定；界面按实测压缩效果给出参考，不预设固定值。

3. 录音存 AAC（单声道 48 kbps），WAV 处理完删除；放行条件见第 9 节。
4. 截图存 WebP，质量约 60。
5. 按年龄降级默认开启，取保守的默认天数（第 9 节）；你可以改天数或关闭，只按存储上限整理。
